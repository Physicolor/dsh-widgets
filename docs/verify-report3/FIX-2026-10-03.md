## 1. yield beat 在反复重载后失效（车主报的「兼容效果不好」的主因）

**根因**：`measure.ts` 原先用模块级 `let frameEl` 缓存 frame 元素，只在「右栏网格列
断连」时调用 `bindFrameTransition()` 重绑。shell 在某些路径下会重建 frame 节点而
**不**断开右栏列 —— 此时旧监听器挂在已脱离文档的节点上，`document` 上再也收不到
`transitionrun(grid-template-columns)`。吞噬的「同步让位」是一拍（beat）的事：收不到事件
就退化成 240ms + 520ms 的两级轮询兜底，用户看到的就是「侧栏滑进来、组件栏还在原地，
过一会儿才跳开」。

**修法**：改成托管在 document 捕获阶段的单一监听器，不再依赖任何元素引用：

```ts
const FRAME_CLASS_SUFFIX = '_frame'
function isFrameElement(el: EventTarget | null): boolean {   // :155
  for (let i = 0; i < cls.length; i++) if (cls[i].endsWith(FRAME_CLASS_SUFFIX)) return true
}
function onTrackTransitionRun(event: Event): void {          // :143
  if ((event as TransitionEvent).propertyName !== 'grid-template-columns') return
  if (!isFrameElement(event.target)) return
  ...
}
// install()                                          :580
document.addEventListener('transitionrun', onTrackTransitionRun, true)
// disposer                                           :626
document.removeEventListener('transitionrun', onTrackTransitionRun, true)
```

`let frameEl`、`bindFrameTransition()` 及其在 `observeMeasured()` 里的调用全部删除。

**实测**（`scripts/diag-yield-beat.cjs --rounds 4`，断开重连 4 轮；预算 120ms）：

```
round 1  real beatLag=1ms (sync-on-event=true) · control beatLag=no-beat
round 2  real beatLag=0ms                      · control beatLag=no-beat
round 3  real beatLag=0ms                      · control beatLag=no-beat
round 4  real beatLag=0ms                      · control beatLag=no-beat
worst real beatLag across 4 reload(s): 1ms (budget 120ms)   ALL CHECKS PASSED
```

control 轮次的 `transitionrun=null` 是有效对照：证明对照组确实收不到事件、兜底路径生效，
而实验组每一轮都是**事件同步拍**，不是轮询碰巧撞上。

## 2/3. 吞噬路径上的两处多余写入

**根因 2**：`updateRailBudget` 每帧无条件 `drawer.setAttribute('data-yielded', ...)`。
`dsh-ui-harmonizer` 在该抽屉上挂了 MutationObserver，任意属性变更都会触发其
`refreshMaterial`（实测 12–27ms/次，trace 里 `detectGlass ← refreshMaterial` 10 次）。

**修法**：值比较后写。

```ts
const wants = space.yielded
if (wants !== drawer.hasAttribute('data-yielded')) { ... }
```

**根因 3**：`measureRailTop` 在读完若干 `getBoundingClientRect()` 之后、又读下一个 rect
之前，中间写了一次 `setVar('--dsx-rail-top', ...)`。`:root` 上的自定义属性写会让
**整个文档**的样式失效 —— 于是后面每一次 rect 读取都变成一次全文档强制重排。
这是插件自身最大的一处强制布局来源。

**修法**：函数内改成「先读后写」，全部写入集中到函数尾部：

```ts
// ── READS FIRST, WRITES LAST ──          :522
setVar('--dsx-rightbar-w', ...); setVar('--dsx-rail-top', ...)
setVar('--dsx-input-bottom', ...); noteRailTop(railTop)      // :541-542
```

节流分支（`VERTICAL_PROBE_INTERVAL_MS = 250`，:92）里补写 `--dsx-rightbar-w`，保证
「延后重测」不会漏掉宽度更新；composer 盒子改为复用已有 rect
（`comp === dock ? dockBox : comp.getBoundingClientRect()`）；顺手删掉死变量
`--dsx-rail-avail`（有写无读）。

## 4/5. 组件栏尺寸与逐帧变量写

**根因 4**：`.dsx-stats-rail` 是 `position: fixed; top: var(--dsx-rail-top); bottom: 0;
box-sizing: border-box`，所以 `clientHeight = window.innerHeight − --dsx-rail-top` 是
恒等式；而 ResizeObserver 的 `contentRect.height` 是 **content-box**
（= `clientHeight − 4px − padding`），两者不可互换。`rowFitSide` 原先走
`shellRead('railInnerH', () => rail.clientHeight)` —— 一次同步布局。另外
`readChatMeasure` 每次 `getComputedStyle(host)` 取 `--dsh-chat-user-width`，而该变量
本来就写在 inline style 上。

**修法**：`geometry.ts` 新增已发布 rail 顶点的旁路通道，`rowFitSide` 直接算：

```ts
let notedRailTop = -1                                   // :83
export function noteRailTop(top: number): void           // :86
export function clearRailTop(): void                     // :91
const innerH = notedRailTop >= 0
  ? Math.max(0, window.innerHeight - notedRailTop)
  : shellRead('railInnerH', ...)                         // :540-541
```

`measure.ts` 在写 `--dsx-rail-top` 的同一处调 `noteRailTop(railTop)`，disposer 里
`clearRailTop()`。`readChatMeasure` 加内联快路径：

```ts
const inline = Number.parseFloat((host as HTMLElement).style.getPropertyValue('--dsh-chat-user-width'))  // :242
if (Number.isFinite(inline) && inline > 0) return inline
```

**根因 5**：`rail-view.tsx` 每帧三连写 `--dsx-rail-w` / `--dsx-rail-pad` /
`--dsx-rail-overshoot`，其中 `--dsx-rail-overshoot` 全仓没有任何读取者；另外
`setRailPaneH` 用了函数式 updater，每次 commit 都要先读 `rail.clientHeight`
（该 updater self-time 130.9ms，是 E2 关闭帧里最大的自有项）。

**修法**：`geometry.ts` 导出带等值短路的 `setRailVar(name, value)`（:405），
`rail-view.tsx:641-643` 三处改走它，死变量 `--dsx-rail-overshoot` 的写删除，
`:248` 改为直传 `setRailPaneH(rail.clientHeight)`。

## 6. 折叠波峰期间的强制布局/样式（本条是本次最强的证据）

**根因**：`RailWave.tsx` 的 `syncWholeCards` 在每次 `useLayoutEffect` 里读
`rail.scrollTop` 与 `rail.clientHeight`，用它们算可见带（band）。该 effect 在折叠动画
的每一帧都会跑，于是每一帧都强制同步布局；同时它的依赖是对象身份，而
`wave-geometry.ts:221` 每次渲染都重建 `staticLayout`，导致无依赖 effect 反复执行。

**修法**：`syncWholeCards` 去参数化（`:843`），改用组件已经持有的缓存值：

```ts
if (paneH <= 0) return
const band = { lo: railScrollTop - RAIL_TOP_INSET, hi: railScrollTop - RAIL_TOP_INSET + paneH }
```

再补一重**数值指纹**守卫（`lastCutKeyRef`，:867），因为对象身份判断在这个组件里天然失效：

```ts
const lastCutKeyRef = React.useRef<number[]>([])        // :867
// key = [wholeCards ? 1 : 0, railScrollTop, paneH, side, restAdd.top, ...restLayout 的 top/h]
```

**实测（Chrome tracing，`--what=fold --reps=5`，headful 1707×1067 @ DSF 1.5）**：

修复前强制布局栈（逐字）：

```
20x check@inline:7229 ← raf@inline:7249
17x merged-chunk…&rev=4e77c67c6b0f:21638 ← gi ← Lu        (官方 shell React)
10x detectGlass:38646 ← refreshMaterial:38698             (dsh-ui-harmonizer)
 9x bandOf:25732 ← syncWholeCards:25759                   ← 本条修复的目标
 5x measureRailTop:24966
 1x groupDurationMs:26596
 1x place:38341 ← showNow:38370                           (dsh-notification)
```

修复后：

```
19x check@inline:7229 ← raf@inline:7249
17x merged-chunk:21638 ← gi ← Lu
10x detectGlass:38744 ← refreshMaterial:38796
     bandOf ← syncWholeCards          ← 已从强制布局栈中消失
 7x measureRailTop:25012

```

强制样式栈同样：`bandOf ← syncWholeCards` 由 14 次降为 0（其余项同量级）。

**⇒ 9 次强制布局 + 14 次强制样式被从动画帧里彻底摘掉，前后栈名逐字可对。**
这是「性能不退化」的正面证据：不是提速，而是把同步重排移出了动画路径。

折叠 fps 对照：52.2（PRE）→ 49.7（POST）fps（234 rAF/4.5s vs 245 rAF/4.9s），

在噪声内。**本次没有「折叠 fps 提升」这个结论，也不应声称。**

## 7. 折叠时 13 张卡各触发一次强制布局

**根因**：`CardBody.tsx` 的 `useLayoutEffect` 每次执行都调
`el.setAttribute('data-dsx-overflow', '1')` 或 `removeAttribute`，无论溢出状态是否
变化。任意属性变更都会使该节点局部样式失效，下一帧重新计算 —— 13 张卡在折叠期间
各命中一次，该 effect self-time 44.2ms。

**修法**：加 ref 守卫，只在翻转时动 DOM。

```ts
const overflowRef = React.useRef(false)                  // :260
if (overflow === overflowRef.current) return             // :270
overflowRef.current = overflow                           // :271
el.removeAttribute('data-dsx-overflow')                  // :273
el.setAttribute('data-dsx-overflow', '1')                // :277
```

## 已知代价（结构性，未做）

- **E1/E2 的 p95 档位由官方 `grid-template-columns` 轨道动画本身决定**。官方的右侧栏
  就是 `[class$="_frame"]` 的第三条网格轨道，`transition: grid-template-columns` 是
  **主线程布局**动画，不是合成器动画。插件无论怎么优化都改不了它的振幅 —— 这正是
  「展开/收起本身就有 2 帧卡顿」的物理来源。
- 要真正丝滑只有一条路：把右侧栏从「推开内容」改成「覆盖滑入」，用
  `transform: translateX()` 做合成器动画。这是**产品决策**，会改变观感与
  `minmax(400px, 1fr)` 的布局语义，本次未采纳。业界报告
  （`docs/reports/sidebar-animation-performance.md` 第 7.4–7.6 节）记录了这条硬取舍
  与 `[data-animating]` 陷阱。
- 官方右栏宽度只能通过 `[class$="_handle"][data-side="rightbar"]` 拖动条调整，布局状态
  在内存中，重载即复位，无公开宽度 API。
