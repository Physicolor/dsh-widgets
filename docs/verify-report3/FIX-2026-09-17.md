# 2026-09-17 report — three symptoms, root causes, final resolution

Reported (车主):
1. 在已有对话中新建对话会**偶现**组件区域未正确隐藏，且**稳定**出现组件区域未立即隐藏。
2. 打开右侧边栏 / 组件区域后，DSH 的对话导航（轮次导航）被遮挡或消失。
3. 悬浮对话导航时，被对话区域的左右拖动条压住（截图为证：指针位置显示的是拖动条手柄光标）。

## 1. 组件区域未隐藏（已修，5/5 复现 → 5/5 修复）

**根因**（`newconv-flake.json`、`after-newconv.json`）：`useBridge` 用 `useState` + 订阅
effect。新建对话时 shell 会在**同一帧窗口**内挂载新对话的 `conversation.input.overlay`
槽（抽屉就在这里），同时卸载上一会话的 `conversation.composer.dock` 槽（`hasSession`
的唯一信号源）。若 `setState({hasSession:false})` 的 emit 落在「新条目已渲染、effect
尚未 flush」之间，新实例**永远收不到那次 emit**，快照停在 `hasSession:true`：rail 一直
在、`opacity:1`、`elementFromPoint` 命中它（真在拦截指针），而 `body.dsx-stats-active`
已被模块级订阅者摘掉（两个消费者自相矛盾）。手动 `dispatch({...snap, hasSession:false})`
立刻消失，证明 React 树活着、只是没收到更新。

**修法**：`useBridge` 改 `React.useSyncExternalStore(subscribe, getBridgeSnapshot)`（订阅后
重读快照并对差异强制重渲染，正好覆盖丢失窗口）；快照每次 `emit` 重建一次（引用稳定）。
外加 `body.dsx-stats-no-session` → CSS 立即 `visibility:hidden` 整个 `.dsx-stats-drawer`，
会话交接**瞬时**隐藏（手动关闭仍走 0.3s 滑出）。

实测：修复前 5/5 轮 rail 一直留在页面上（最长观察 6s 仍在拦截指针）；修复后 5/5 在
~300ms 内不可交互、1.5s 内卸载。

## 2/3. 对话导航（轮次导航）

**测量结论**（`nav-geometry.json`、`nav-matrix.json`、`nav-container`、`width-overlap`）：

- 导航由官方 `TurnNavigator.module.css` 的 `@container (width <= 900px)` 控制，容器是转写
  滚动器（`container-type: inline-size`）—— **正是我们 yield 缩小的盒子**。rail=372 时：
  1600 视口容器 874 → 导航 `display:none`；1760 视口 → 可见。**这是"组件区域把导航挤没"的
  真实机制**，也是它的代价来源。
- 导航与 rail **从不几何重叠**（任何宽度都留 22px）；右侧边栏打开时官方面板确实画在插件
  所有层之上（像素比对 + `elementFromPoint` 命中 `geFEbW_guide`）。
- 导航被拖动条压住：`clearance = (盒宽 − contentWidth) / 2 − 109`（12 组配置实测律）。
  DSH 自己的 `CONTENT_EDGE_BUDGET = 176` 只给拖动条留位、**没给导航留位**，所以转写拖宽时
  两者原生就撞（rail 关闭、claim=0、1440 视口 + 1000px 转写 → 重叠 26px）；我们的 yield
  把这条 gutter 再削掉一半，于是提前撞（1600 + 850px 转写 + rail 开 → clearance −40，
  指针命中 `wSkVaW_widthHandle`，正是截图那一幕）。

**最终决策（车主裁定）**：**不动 rail 的布局**，改为修**命中优先级**。

- 官方把 40px 拖动带画在 `z-index: 8`、导航槽在 `7`，重叠处拖动带抢走 hover。
  `widgets.module.css` 新增一条规则把导航槽提到 `9`：
  `[data-conversation-scroll] :has(> nav[aria-label]) { z-index: 9 }`
  —— 用"包含导航 nav"来定位，而不是 hash 类名，产品重建也不会静默失效。
- **不**再为让开拖动带而收缩 rail：早前一版按 clearance 上限收缩 claim，会把 1400–1600
  宽度下用户的 2 列挤成 1 列（车主明确要求撤回，已全部回退）。

验证（`verify-nav-click.cjs`，1600 视口 + 1200px 宽转写，拖动带与导航重叠的几何）：

```
navigator {"x":1352,"right":1380} | drag band {"x":1365,"right":1405}
band overlaps navigator: true
hovered element over the band: {"cls":"eGxaPq_markPosition","isNav":true}   ← 导航赢得指针
click result: width-drag started=false                                     ← 不再误起拖动
```

rail 尺寸与修复前完全一致（`diag-nav-matrix.cjs`）：1440 → 198、1600 → 372、1760+ → 372。

**已知代价（车主已接受）**：rails 仍会按空间阶梯收缩（1440 下 1 列是空间不足，与本次改动
无关）；1600 及以下窗口 + rail 开启时，我们的 yield 会把转写容器压到 900px 以下，DSH 自己
就把导航隐藏。要同时保住"2 列 rail + 导航常驻"，只能改 yield 的作用对象（只缩消息内容、
不缩转写盒）——那是一处结构性改造，未做。
