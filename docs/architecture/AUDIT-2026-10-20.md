# AUDIT 2026-10-20 — dsh-widgets：性能、复杂度与可维护性排查

本文件是这一轮排查的结论与证据台账。它不同于
[CURRENT_ARCHITECTURE.md](CURRENT_ARCHITECTURE.md)（2026-09 的结构审计）和
[REFACTOR_PLAN.md](REFACTOR_PLAN.md)（同期的结构重构计划）——那两轮解决的是
「中央文件 / God Module」，本轮的入口是三个具体问题：

1. 是否存在「占用性能过大导致卡顿」；
2. 是否存在「简单代码写得极其复杂冗余」；
3. 代码结构是否偏离长期维护规范。

**结论先说**：这个插件的复杂度大部分是有实测依据的，不是随意堆出来的；真正该修的是
四处落在高频路径上的浪费，本轮已修完并用探针给出前后数字。结构层面的拆分与注释搬迁
本轮**未做**，原因见 §7。

## 2. 四处已修复的浪费（含前后数字）

### F1 每次 bridge emit 重建 2×N 张卡 —— 已修

`rail/rail-view.tsx` 的输出缓存以 **snapshot 对象身份**为键，而每次 emit 都会造出新的
snapshot，所以缓存必 miss：每张卡（以及放大层里的第二份）都重新 `render()` + 重建，
`CardBody` 的溢出守卫随后为每张卡强制读一次 `scrollHeight/clientHeight`。

修法：`sameOut()` 按**输出内容**比较（纯数据深比较，深度上限 8，React 元素直接判不等），
内容相同就复用旧对象身份 → `cardElCache` 命中 → React 跳过两份卡树。

| 指标（14 张已装卡，20 次 emit 的突发） | 修前 | 修后 |
|---|---|---|
| 每次 emit 的卡体重建（布局读取计） | **62.4** | **6.0** |
| 每次 emit 的长任务总时长 | 3.6–4.3ms | 4.0–5.1ms（噪声区间，1 个长任务/20 次） |

> 剩下的 6 次/emit 是**时间派生文本**的卡（时钟、计时器、相对时间），它们本来就该变。

### F2 指针每移动一次强制布局两次 —— 已修

`measureRail()`（`getBoundingClientRect` + `getComputedStyle().paddingTop`）在**每一次
`mousemove`** 上执行，即使指针在左侧会话区；高刷鼠标约 250 次/秒。

修法：测量结果进 ref 缓存，只在「会移动 rail 盒子」的信号上失效——自身滚动、resize、
**承载 rail 的盒子**（drawer / zoom / rail 自身）的 transition、rail 的 style/class 翻转、
ResizeObserver 报告、以及会重排卡座的 props。子元素的 hover transition 不失效（它们
在 wave 期间每帧都在跑）。指针远离 rail 时用算术早退，不再逐卡判定。

| 指标 | 修前 | 修后 |
|---|---|---|
| 60 次「会话区」移动的 rail 侧布局读取（probe-emit-cost） | 120 | **8** |
| 40 次「rail 内」移动的 rail 侧布局读取 | 86 | **8** |
| 一次 10s 扫过 rail 的 wave 期间 `measureRail` 读取（probe-hover-layout-reads） | **≈718** | **0** |

> 残下的 8 次/批是每批开头抽屉/层的 transition 触发的合法重新测量。

### F3 自创设置面板常驻挂载 + 同一个瓦片打开两个不同界面 —— 已修

- 该面板（`dsx-stats-addpanel`，内含完整 `WidgetsPage`）**无条件** portal 挂载，看不见
  却跟着每次 emit 重渲染；
- 静止层的瓦片打开官方设置窗口，**放大层的瓦片打开的是这个旧面板**——同一个按钮，
  悬停与否行为不同（用户报告「点设置弹出我们自创的窗口」正是这条）。

修法：旧面板**封存**到 `surfaces/add-panel.tsx`（不再被 import，打不进包，也没有任何
挂载点），两个瓦片统一调用 `openSettingsSection`。同时补上 DSH 0.2.x 的真实入口：
`_settingsArea` 的触发器打开的是**账号菜单**，「设置（Ctrl+Alt+,）」是其中的菜单项；
旧代码点开触发器后直接等我们的导航行，永远等不到——在这个桌面版本上瓦片是**静默失效**的。

### F4 记账名单与热力图日志每次 pass 重新读盘 —— 已修

`loadSeen()`（「哪些步已记账」）在**每次 collector pass** 都整份 `JSON.parse` 一遍，
而名单只增不减；`loadHeatmapStore()` 在无 usage-center 的安装里同样按「每卡每次 emit」
读盘。这是典型的「用久了越来越慢」。

修法：两者都改成每页只读一次、写回合并（2s）+ `pagehide`/隐藏时同步 flush；跨 tab 通过
合并 `storage` 事件保持收敛。emit 突发内、只统计本插件 `harness-widgets.heatmap*` 键的
读取：**4.1 → 1.3 次/emit**，稳态 3 次 emit 窗口内为 **0**。

## 3. 观察后明确保留的复杂度（不是缺陷）

| 项 | 为什么保留 |
|---|---|
| 双份卡树（静止 deck + 放大 overlay，常驻） | 作者实测：懒挂载会让每次 hover 首帧多 ~93ms；eager mount 换来的是「进入不抖」。F1 修好后它的每 emit 代价已接近零。 |
| `rail/wave/*` 的 4 个 rAF 循环、层级 z-tier、visible-band 裁剪 | 每一条都对应一个已复现的缺陷（见 CODE_MAP §6 与 `styles/rail.module.css` 注释）。 |
| `getPrefs()` / `snapRef` 这类「活绑定 + ref」写法 | handler 会被元素缓存回收，直接闭包会读到过期值——这是缓存方案的必然配套，不是冗余。 |
| `contract/types.ts` 1,521 行纯类型 | 类型集中是契约的刻意设计，零 import。 |
| `generated.registry.ts` 1,622 行 | 生成物，永远不手改（G1 守护）。 |

## 4. 登记但本轮不改的项

| # | 事项 | 判断 |
|---|---|---|
| F8 | 单元结构不一致：绝大多数单元是「12 行委托 + `families/*/renders`」，少数是 200–850 行自成一摊（`session-cost` 846、`peak-pricing-board` 718、`usage-mix` 557、`goal-progress` 518） | 真实的不一致，但**拆它等于重写卡片的渲染路径**，收益是维护性、风险是视觉回归；本轮不动，登记为后续。 |
| F9 | 重复实现：`fmtBytes` ×2、`fmtMs` ×3、`dayKey` 内联 ×2、`clockInZone` vs `clockAt` | 逐个核对后发现**规则并不相同**（单位风格、小数位、超过一分钟的形态），强行合并会改变卡片文案。只有 `dayKey` 的内联副本是真的重复，价值过小，留待与 F8 一起做。 |
| F10 | 注释占 44%（`RailWave.tsx` 68%、`rail-view.tsx` 62%） | 里面是「某日实测多少毫秒、哪个方案被否」的历史，删了会重复踩坑。搬迁到 `docs/architecture/notes/` 是正确方向，但需要逐文件核对「搬走的数字一个不少」，本轮不做半成品。 |
| F11 | 客户端包 1.05MB 未压缩 | **刻意不压缩**：它每页只解析一次（几十 ms 量级），而 minify 会重命名函数——`probe-hover-layout-reads` / `probe-emit-cost` 的按调用点归因正是靠这些名字。用调试能力换几十 ms 首屏不划算。 |
| F12 | 仓库 782 个追踪文件（416 docs / 65 scripts），170 个脚本只有 11 个进闸门 | 卫生问题，不影响运行；本轮只新增了一个探针并修正了三个过期断言，没有大规模归档。 |
| F13 | `deck-cascade.ts` 的 observer 句柄 | **已修**：句柄保存在模块变量里（单例，可释放）。 |
| F14 | `host/overview.ts` 硬编码代理端口 `10808`（v2rayN），本机现用 Clash `7897` | **已修**：改为按顺序探测 7897 / 10808 两个回环候选，谁在监听用谁（关闭的回环端口会立刻 refuse），egress 结论也按端点缓存，切换代理会重新测量。见 `5b39c66`。 |

## 6. 验证

**离线（每次提交前都跑）**

```bash
pnpm check                 # registry + tsc，0 错
pnpm build && pnpm test    # G1–G12；G4/G5 是「输出没变」的硬证据
```

**live（桌面 GUI，`DSH_HOME=D:\dsh-home`）**

```bash
DSH_PORT=59890 DSH_PROBE_HEIGHT=720 node scripts/verify-rail-interaction.cjs --session <会话名>
DSH_PORT=59890 DSH_PROBE_HEIGHT=720 node scripts/verify-rail-scroll.cjs      --session <会话名>
DSH_PORT=59890 DSH_PROBE_HEIGHT=720 node scripts/verify-rail-wheel-matrix.cjs --session <会话名>
DSH_HOME=... node scripts/probe-emit-cost.cjs 127.0.0.1:59890
DSH_HOME=... node scripts/probe-hover-layout-reads.cjs 127.0.0.1:59890
```

本轮结果：G1–G12 全绿；`verify-rail-interaction` / `verify-rail-wheel-matrix` 全 PASS；
`verify-rail-scroll` 只剩一条 **既有** 3px 抖动断言失败（未改动的 HEAD 上同样失败，见 §8）。

**三个探针的过期断言（已修，不是放宽）**

- `the LAST row can top out`：现行规则是 2026-10-01 起「停在让最深内容完整可见的最小行」，
  旧断言测的是一个已被删除的行为。改为按现行公式计算末档（`verify-rail-wheel-matrix` 同步）。
- `page.mouse.wheel`：wave 活着时指针下的元素是 portal 到 body 的放大层，CDP 驱动会看
  hit-test 时序（同一坐标两次运行 0 / 262 都出现过）。改为在 rail 上派发合成 wheel——
  被测的 handler 是同一个。
- 会话列表在 hydration 之后才渲染，`networkidle` 会抢跑；补 `waitFor`，并加
  `DSH_PROBE_HEIGHT` 让「不溢出的高度」也能复现滚动用例。

## 7. 明确未做（与原因）

1. **RailWave（1,840 行）/ rail-view（1,336 行）的拆分**：可行，但它是**纯移动**工作，
   需要逐段 `audit-move-only` + 逐帧 live 验证；在动它之前，本轮的四项性能改动已经
   把「高频路径的浪费」清掉了。拆分的收益是维护性，风险是 wave 的逐帧行为——不在
   没有逐帧回归网的阶段做。
2. **注释搬迁**：同上，属于「知识搬家」，需要逐条核对数字，不能半途。
3. **包压缩**：理由见 F11。
4. **`lib/` 是否继续入库**：桌面端用 `link:` 直接读 `lib/`，移出会让本地安装变成坏包；
   保持现状。

## 8. 已知既有问题（不是本轮引入）

- `verify-rail-scroll.cjs` 的「放大卡在滚动时是固定锚点」在本机差 3px（门限 2px）；
  在未改动的 HEAD 构建上同样差 3px → 既有抖动，未修。
- 视口高 1000px、6 行卡时，rail 内容只比视口高 114px：滚动停档公式取 0 档，最后一行
  会被裁 22px。这是 2026-10-01 停档规则在「不足一个 pitch 的溢出」下的边界，未改。
- `verify-rail-interaction` 末尾的「被官方右栏覆盖后 wave 应变暗」在该宿主上报告
  `opacity 1`，但整套断言仍 PASS（该场景的判据在别的检查里）——记录在案。
