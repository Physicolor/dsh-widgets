# 第三批·修订轮的组件审计（2026-09-29）

> 车主的原话：**「以后每次你做组件的时候一定一定要和现有的组件做审计和对比：有没有功能高度重合的地方？应该合并，分化赛道吗？怎么样让用户清楚的了解二者之间的区别？这个组件有必要被展示吗？有没有其它已存在的更方便的形式某些信息已经被展示？」**
> 本文是这句话在第三批上的执行结果：逐条给出结论与**落地动作**，并把那份问卷变成每次开工的强制前置（见 §5）。

---

## 1. `model-config` 会话配置 —— **删除**

**结论**：不该存在。输入框的模型选择器已经常显**模型 + 推理档**，而这张卡把同样的两件事搬到 rail 上，属于规范第 8 条「不重复既有信息」的直接违反，且它占了 150px 的一个格子。

**落地**：`src/widgets/model-config/` 整个目录删除（连同 registry 重生成）。项目数 56 → 55。

**教训（写进 §5 的第一问）**：判断「有没有别处已经更方便地展示了」时，**要把产品自身 UI（输入框、页头、设置页）也算进"现有组件"**，不只是 rail 上的 widget。

---

## 2. `window-forecast` ↔ `quota-manage` —— **分化，不合并**

| | `quota-manage` 额度管理 | `window-forecast` 限流预测 |
| --- | --- | --- |
| 窗口 | **月账期** | **5h / 周**（短期限流窗口） |
| 大数字 | 账期**预测百分比**（月末跑到多少） | 两个窗口里更危险那个的**重置时占用百分比** |
| 回答的问题 | 「这个月会不会超？**今天还能用多少**？」（预算/花钱） | 「**会不会在重置前被打满**？还有多久被限流？」（会不会被打断） |
| 明细 | 今日用量 / 今日推荐（token 预算） | 5h / 周 / 剩余重置 |
| 时态 | 计划（往前看一整个月） | 预判（往前看几个小时） |

**为什么不合并**：两者窗口不同、单位不同（token 预算 vs credits 占用）、且回答的是**两个不同的决策**——"我这个月还能敞着用吗"和"我这条长任务会不会中途被掐"。塞进一张 150px 卡会同时丢掉两个答案。

**为什么之前会被看成一回事**：两张卡的大数字都是**百分比**，且标题都没说清窗口。这是**表达问题，不是功能重复**。

**落地动作**：
- 标题 `窗口预测` → **`限流预测`**（Throttle Forecast）：把"会发生什么"写在名字里，不再像"额度"。
- 灰字已含窗口名与判定（`5h · 预计 1h14m 后打满`），保留 —— 它已经回答了"这是哪个窗口"。
- 两张卡的 `README` 各加一节交叉引用（§2 表格照抄）。

## 3. `session-cost` ↔ 其它「钱」卡 —— **分化，不合并**

| 卡 | 口径 | 单位 |
| --- | --- | --- |
| `cc-usage` | **账号**在某账期内的请求数/成功率/token/花销（provider 报的） | provider 自己的钱 |
| `quota-manage` | **月账期**的额度占用与今日预算 | credits + token |
| `usage-mix` | **跨平台额度**总览 + 今日 token | 占比 |
| **`session-cost`** | **本会话**的四桶 token，按价格表折算 | 钱（带 `sourceType` 出处） |

**结论**：`session-cost` 唯一，它是**唯一把"这次对话"折成钱**、也是唯一**读价格表**的卡。与 `cc-usage` 的区别是**范围**（本会话 vs 账号账期），与 `quota-manage` 的区别是**问题**（花了多少 vs 还能花多少）。

**落地动作**：标题 `会话成本` → **`本会话成本`**，把范围写进名字（这也是它和账号级钱卡最容易混的地方）；README 加交叉引用表。

---

## 4. `subagent` ↔ `jobs` —— **分化 + 去噪（本轮的实质修改）**

**重合点（真实存在）**：`jobs` 的 `kind` 里就有 `subagent`；两张卡都在回答「有几个子东西在跑」。车主的怀疑是对的。

**但两者看的是两套东西**：
- `jobs` 读**后台作业注册表**：有真实 `status`（running/completed/failed）、起止时间 —— 回答「有没有活正在占着机器」。
- `subagent` 读**子会话目录**：只有身份（id / label / 一次性 vs 可持续 / 创建时间）—— 它**拿不到**运行状态。

**分化后的职责（写进两张卡的 README）**：
- `jobs` 继续做「运行中的作业」；`subagent` **不再以"活了多久"为主角**（那是 jobs 的语义），改为**回答"派出去的是些什么"**：几个、几个是可持续的、分别是谁。
- 因此：大数字仍是**总数**；明细改为「可持续 N / 总数」「最近 <label>」等**身份类**读数；**去掉琥珀色**（子代理不需要危险/警示色，见 §5 第 6 问）。
- 灰字必须**自己说清是什么**：`最久活跃 47m56s`（而不是光秃秃一个时长）。

**仍未解决的一处（记录）**：`subagentCatalog` 不携带状态，所以这张卡**永远不能**说"N 个运行中"。它回答"派了几个/都是谁"，"还在不在跑"归 `jobs`。这是数据面的硬边界，不是设计选择。

## 5. 强制前置问卷（已并入 `WORKER-BRIEF-V3.md` §0）

每新建或改版一个组件，**开工前**必须逐条回答并写进该组件 `README.md` 的第一节，**答不上来就不许开工**：

1. **这个信息是不是已经在别处更方便地展示了？** —— 包括产品自身 UI（输入框的模型/推理档、权限选择器、页头）、设置页、以及既有 rail 卡。有一处更方便 → **不做**（`model-config` 就是这么死的）。
2. **有没有功能高度重合的既有组件？** 列出它们的名字与口径，逐条说清差异（窗口 / 范围 / 单位 / 时态）。说不出差异 → **合并**或**放弃**。
3. **如果保留两张，用户怎么在不读文档的情况下分清？** —— 名字、大数字的**单位**、灰字的第一句必须自己回答"我是哪个"。**反例**：`窗口预测` 与 `额度管理` 都印百分比，所以前者改名 `限流预测`。
4. **这个大数字是什么单位、什么范围、什么时间点？** 一个用户需要被解释才能看懂的数字 = **不合格**（`0 / 256` 就是这么被打回的）。
5. **它应该一直在，还是可以消失？** 会因数据缺失而"突然出现/消失"的卡会打乱用户的布局 —— 用户**主动装进 rail** 的卡，缺数据时应显示**安静的空态**，而不是隐藏自己。
6. **颜色有没有被赋予一个用户能说出的含义？** 绿/黄/红只表示**危险或警示等级**。没有等级含义的量**不许染色**（子代理的琥珀色就是因为答不上这一问被撤掉）。

---

## 6. 本轮同时固化的两条表达纪律

- **一个读数只印一次**（原有纪律，本轮再确认）：`sys-disk` 的第一行灰字与图表重复、`subagent` 的灰字与首行重复，都要消掉。
- **空态要"安静"，不要"占位"**：插电时「剩余」不该印 `—`（那是一个不存在的读数占了一个位置），直接不显示；没有目标时的目标卡应显示一行安静的说明，而不是 `0 / 256` 这种看似有值实则无义的数。
