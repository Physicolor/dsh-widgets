# 后台任务（`jobs`）

> 本部件的一切都写在 `src/widgets/jobs/` 内：`manifest.json` + `index.ts` + 本 README。
> 没有新增渲染原语，没有改任何共享层文件。
> 目录名 / widget id / 契约字段仍是 `jobs`（生产者的内部名），只有**用户可见的名字**是「后台任务」——见 §10。

## §0 审计（WORKER-BRIEF-V3 §0，动手前先逐条回答）

1. **这个信息是不是已经在别处更方便地展示了？**
   有一处**部分**覆盖：官方页头的 jobs 弹层（`@deepseek-ai/dsh-client-ui-jobs`）读的是同一份
   `jobsBySession` 镜像。但它有两条硬限制：① **只有存在任务时才出现**
   （该插件「renders nothing at all until the session has at least one job」）；
   ② 必须**点开**才能看见，且它是「有没有 / 有几个」的入口，不是读时长的地方。
   所以「机器被占了 12 分钟」这件事在 rail 上原本**没有任何被动可见的载体**，而长命令正是
   「会话看起来卡住」的头号原因。卡片补的是**被动可见 + 全部结束后仍然在场**（见第 5 问）。
   → 结论：**保留**。
2. **有没有功能高度重合的既有组件？** 逐条列差异（窗口 / 范围 / 单位 / 时态）：

   | 卡 | 读什么 | 窗口 / 范围 | 单位 | 时态 |
   | --- | --- | --- | --- | --- |
   | **`jobs` 后台任务** | `jobsBySession` 注册表（有真实 `status` 与起止时间） | 本会话 | **个**（占着机器的任务数）+ 时长 | **进行时**（此刻什么在占机器） |
   | `subagent` 子代理 | 子会话目录（只有身份，**无状态**） | 本会话 | 个（派了几个 / 几个持续型） | 身份（都是谁），不回答"还在不在跑" |
   | `tool` 工具调用 | 会话节点里的工具调用 | 本会话 | 次 / 毫秒 | **已结算的历史**（调用早已返回） |
   | `task` 任务 | 会话 todo 列表 | 本会话 | 个（进行中 / 待办） | 清单状态，**不是进程** |

   `jobs` 的 `kind` 里确实有 `subagent` 一类（重合点真实存在），但两者读的是两套数据：
   `subagentCatalog` **不携带状态**，`jobs` 的 `status` 才是「有没有活在占机器」的唯一来源。
   这条分化写在 `docs/research/BATCH-3-AUDIT.md` §4，本节与它一致。
   → 结论：**不合并**（差异是数据面的硬边界，不是设计选择）。
3. **如果不合并，用户不读文档怎么分清？**
   名字：`后台任务`（背景进程）vs `任务`（todo 条目）——「后台」二字就是分界。
   大数字的单位：`jobs` 的大数字是**占着机器的进程数**（此刻），`task` 的大数字是**清单条目数**（含待办）。
   灰字第一句：`jobs` 是 `最久 12m4s · 共 4 个`（时长），`task` 是 `进行中 · N 待办`（清单）。
   三个维度都不重合，用户可以只看一眼就分清。
   （本轮改名 `后台作业 → 后台任务` 实际上**拉近**了与 `任务` 的字面距离，所以这一问是改名后
   必须重新回答的：仍然成立，因为 `后台` 一词专指"脱离本次对话在前台之外继续跑的东西"，
   而 `任务` 卡说的是待办清单——但这是本卡最容易与邻居混淆的一处，记录在此。）
4. **这个大数字是什么单位、什么范围、什么时间点？**
   单位：**个**；范围：**本会话**的后台任务；时间点：**此刻仍在占资源的**（`running` + `stopping`
   都算——被要求停止但还没结算的任务仍然占着槽位/进程/文件，排除它会在最需要看见的时候低报负载）。
   它不需要额外解释：标题说了是什么，灰字 `共 4 个` 给了分母，下面三行说明谁在占、最近起了什么、有没有失败。
5. **它应该一直在，还是可以消失？**
   `jobs === null`（部署没有 sessions 服务 / 镜像不可用）→ **整卡 `null`**，因为任何数字都会是编造的；
   `jobs === []`（镜像存在但空）→ **仍然渲染**（`0` + `已结束 0 个` + 三行 `— / — / 0`）。
   理由是这张卡的状态本身就是**用户正在盯着的一个过程的解消**：最后一个任务结束的瞬间把卡藏起来，
   恰好拿走了「全清了」这个唯一有用的确认。它 `defaultInstalled: false`（用户主动装进 rail 的可选卡），
   与 `subagent`（空目录时隐藏）取舍相反，理由写在 §7。
6. **颜色有没有被赋予一个用户能说出的含义？**
   有，且只有一处：**失败行**。`> 0` → `danger`（已经失败是需要处理的事实），`= 0` → `muted`
   （这里的 0 是**真读数**"没出事"，与缺失值 `—` 的 muted 语义不同）。
   大数字（在跑数量）**不染色**：并行跑 3 个只是忙，不是坏，数量没有等级含义。

## 1. 这张卡回答什么问题

**本会话有没有后台任务在占着机器、最久的那个跑了多久、最近起的是哪个、有没有失败。**
一句话：长命令是「会话看起来卡住」的头号原因，而 rail 上原本没有任何地方能看见它。

数据来自客户端 sessions 服务的 **`jobsBySession` 列表镜像**（官方头部 jobs 弹层读的同一份），
**不是投影、不发 RPC、没有加载态**（因此 manifest 里没有 `source` / `skeleton`）。

## 3. 数据来源

读 `WidgetStats.jobs`（契约里写作 `jobs?: JobInfo[] | null`，逐行对应 `SessionJob`）：

| 字段 | 用途 | 口径 |
| --- | --- | --- |
| `status` | 大数字、失败行 | `running` / `stopping` 记为「在跑」；`completed` / `killed` / `failed` 记为「已结束」。**`stopping` 仍占资源**，所以算在跑 |
| `startedAt` | 时长、排序 | epoch **ms**。时长 = `Date.now() − startedAt`（**允许读时钟**，见 §4 与 `index.ts` 头注释） |
| `label` | 最久 / 最近行的名字 | 生产者给的「一行命令/描述」，如 `npm test -- --run`；为空时退回 `kind`（如 `bash` / `subagent`），两者都空才印 `—` |
| `kind` | 名字的兜底 | 生产者种类，也是任务 id 前缀 |

**读时钟是故意的**：运行中任务的「已运行多久」是时钟的函数，不是记录的函数，所以本部件的 render
不是 `stats` 的纯函数——这是 BRIEF §3 明确允许的例外，已在 `index.ts` 里写明。预览用
`meta.sim.now` 把时钟钉住（共享机制里「pinned clock」那种用法），因此相册截图与 G4 快照每次
跑出来的秒数完全相同。

**`null` / `[]` / `—` 各是什么**

| 取值 | 含义 | 卡片行为 |
| --- | --- | --- |
| `jobs === null` / `undefined` / 非数组 | 这个部署**没有任务镜像**（没装 sessions 服务，或采集器还没转发它） | `render` 返回 **`null`**（整卡不出现）。不写 `0`——那会谎报「机器是空的」 |
| `jobs === []` | 镜像存在且为空 | **仍然渲染**：大数字 `0` + 灰字 `已结束 0 个` + 三行 `— / — / 0` |
| 单行缺 `label` 且缺 `kind` | 该任务没有名字 | 名字位置印 `—`（不编造名字），时长照常印 |
| 单行缺 `startedAt` | 无法计时也无法排序 | **该行整条丢弃**（`—` 行加不进任何信息） |
| 无运行中任务 | 「最久」没有读数（已结束任务的**总耗时**是另一个问题） | 该行印 `—` + `tone: 'muted'`，灰字换成「已结束 N 个」 |

## 4. 元素为什么这么摆

- **大数字在标题正下方（`headAfter.big`）**：它回答「现在有几个在占着机器」，是这张卡的主语。
  刻意 **不用 `value`**——`value` 是「正文数字」，在有 `headAfter` 的卡上会被渲染器推进正文重复一次。
- **灰字用 `legend`（数字下面独立一行）而不是 `headAfter.small`**：`small` 只有一个槽位，且要贴在
  数字基线上；这里的信息是「最久 12m4s」+「共 4 个」两段，放进 `small` 会被挤成一个很长的行内串。
  用 `legend` 换来一行 14px，实测仍有余量（见 §5 的高度）。
- **明细三行贴底（`bodyAnchor: 'bottom'`）**：`headAfter` 一行让头部变高，如果正文不贴底，
  多出来的高度会落在三行**下面**，卡片看起来「上重下空」。贴底是本仓库所有 breakdown 卡的姿态。
- **三行是这三个**：最久（谁在占机器）→ 最近（我刚起了什么）→ 失败（有没有出事）。
  三个问题互不重复，且这正是 `tasks` / `tool` 那套「标签左、数值右」的读法。
- **「最近」行没有数值**：它的时长就是「最久」问过的问题（问两遍），所以数值格留空。
  行内只有「最近 <名字>」——这也是为什么长名字必须走**会淡出的标签列**（见下一条）而不是数值列。
- **长名字靠 `breakdown` 标签列的右缘淡出，不写 `…`**：这是 `breakdown.tsx` 自己的契约
  （标签列 `overflow:hidden` + mask 淡出）。数值列是 `nowrap` 且**不设** `overflow:hidden`，
  所以任何长文本都必须待在标签列——本部件把「最久/最近 + 任务名」整串放在标签里，数值列只放数字。
- **本行不给「点击」**：`cycle` 是用量族的池视图机制，这里点一下也没有可切换的意义。

## 5. 语气方向（tone 由本部件决定，渲染器不猜）

| 元素 | tone | 依据 |
| --- | --- | --- |
| 大数字（在跑数量） | **不染色** | 并行跑 3 个不等于坏，只是忙。数量不是严重度 |
| 「失败」行 > 0 | `danger` | 已经失败的任务是需要处理的事实 |
| 「失败」行 = 0 | `muted` | 这里的 0 是**真读数**（「没出事」），不是缺失值；用 muted 与 `—` 的缺失语义区分开 |
| 缺读数（`—`） | `muted` | 「没有这个读数」 |

`killed` **不算失败**：用户主动取消的任务照做了。

## 6. 配置项

无。第一版不加配置：三种状态已经由数据自身决定，三个行各有固定语义，
加一个 `metrics` 选择器只会让 150px 的卡更容易爆高（4 行 = 152px > 150px，见 `index.ts` 的高度预算）。
本轮改名**不引入任何配置项**。

## 7. 空态 / 降级行为

- **`null`（镜像不可用）→ 整卡 `null`**，不占位。理由见 §3 表格。
- **`[]`（镜像为空）→ 仍然渲染**，大数字 `0`、灰字 `已结束 0 个`、三行 `— / — / 0`。
  **为什么与 `subagent` 那张卡相反**：子代理目录在「从不派子代理的会话」里常态为空，
  为空时渲染等于给每个会话加一张永远没内容的卡；而后台任务列表为空，
  是用户**正在盯着的一个状态的解消**——最后一个任务跑完的瞬间把卡藏起来，
  恰好拿走了「全清了」这个唯一有用的确认，也就拿走了这张卡装在 rail 上的理由。
- **单行级降级**：缺名字印 `—`，缺 `startedAt` 丢行，未知 `status` 保留该行但按「已结束、非失败」计。
- **时钟倒挂**（生产者与渲染进程有时差，`startedAt` 在未来）→ 时长钳到 `0`，不印负数。

## 8. 与既有卡的差异（为什么它不是既有卡的重复）

- 本卡以外的 54 张（`src/widgets/` 现有 55 个单元）里**没有任何一张**读 `jobsBySession`（`grep` 在 `src/widgets/` 只有本卡命中）；
  它们回答「用了多少 token / 花了多久 / 哪些工具慢」——都是**已结算的历史**。
  本卡是这批数据里**唯一有真实 liveness 的一张**：它说的是「此刻还有什么在占着机器」。
- 与 **`tool`（工具调用）** 的边界：`tool` 折的是**会话内的工具调用**（节点里的 call/result），
  而 `jobs` 是**后台任务注册表**（`bash` / `subagent` 等生产者注册的长跑任务，官方 jobs 弹层读的那份）。
  一个同步工具调用可能出现在 `tool` 里而永远不在 `jobs` 里；反过来一个后台任务在会话节点里
  只有「已启动」一行，其运行时长只有 `jobs` 有。二者不重叠。
- 与本批的 **`subagent`（子代理）** 卡：子代理卡讲「我派出去的孩子是些什么」，
  本卡讲「本会话的后台任务注册表」（其中有 `kind: 'subagent'` 的行也只是其中一类），
  且两者对空列表的取舍相反（见 §7）。完整对照表见 §0 第 2 问。
- 与 **`task`（任务）** 卡：`task` 是会话 todo 清单（条目状态），本卡是**正在占机器的进程**。
  两者的名字现在只差「后台」二字，所以 §0 第 3 问专门交代了怎么一眼分清。

## 10. 改名记录：后台作业 → 后台任务（与官方术语对齐）

**车主原话**：「后台作业暂时不动，但是名字是不是怪怪的，我记得 dsh 官方的应该叫后台任务」。

**改了什么（只有用户可见的名字，别的一律不动）**

| 位置 | 旧 | 新 |
| --- | --- | --- |
| `widget.jobs.name`（市场卡片名）zh | 后台作业 | **后台任务** |
| `widget.jobs.name` en | Background Jobs | **Background Tasks** |
| `widget.jobs.desc` zh / en | …后台作业… / …background jobs… | **…后台任务… / …background tasks…** |
| `card.jobs.title`（卡面标题）zh / en | 后台作业 / Background Jobs | **后台任务 / Background Tasks** |

**没有改的**：`card.jobs.legend` / `idle` / `longest` / `newest` / `failed` 与 `widget.jobs.simToggle`
的文案（`最久 {longest} · 共 {total} 个` / `已结束 {n} 个` / `最久` / `最近` / `失败` /
`切换 运行中 / 已跑完 / 空列表 预览`）——这些字面里**没有出现「作业」或 "job"**，
按"卡面结构不动"保持原样。键名全部不变（`validate-widget-unit` 查的就是键覆盖率，改键名会红）。

**为什么是「任务」**：官方页头 jobs 弹层自己的中文字典就写「后台任务」——
`@deepseek-ai/dsh-client-ui-jobs`（`lib/types/client/locales.d.ts`，zh 是键集真源）：

| 官方键 | 官方中文 |
| --- | --- |
| `count.live.one` / `count.live.other` | `{count} 个后台任务运行中` |
| `count.idle.one` / `count.idle.other` | `{count} 个后台任务` |
| `list.aria` | `后台任务` |

所以中文侧是**与官方逐字一致**。**英文侧是一处已知的有意偏差**：官方 en 字典仍写
`background job(s)`（`count.live.other` = "background jobs running"），本卡按车主的要求写
`Background Tasks`，好让 zh/en 两张卡说同一件事——若将来要与官方 en 逐字对齐，只需把
`widget.jobs.name` / `widget.jobs.desc` / `card.jobs.title` 的 en 三处改回 `Background Jobs`。

**内部标识符一律不动**（改注释/改名会误导）：widget id 仍是 `jobs`，契约字段仍是 `stats.jobs`，
线上状态仍是 `SessionJob.status`，`index.ts` 里的 `JobRow` / `JobEntry` / `jobsOf` 与全部
英文注释里的 "job" 都**保持**——那是生产者的内部术语，与 `dsh-tool-jobs` / `jobsBySession`
同名同源，改成 "task" 会让代码与数据面漂移。中文件头注释里指代**卡名**的两处
（`后台任务 — this session's…`、`「后台任务全清了」`）已随名字更新。

## 附：实时数据的接线位置（共享层已实现，本沙箱快照稍早）

本部件**只读 `stats.jobs`**。共享层已经落地（主仓库 `184b2d1`）：

- `WidgetStats.jobs?: JobInfo[] | null`，字段为 `{ id, kind, label, status, startedAt, finishedAt?, detail? }`
  （`status` 是 `running | stopping | completed | killed | failed`）；
- 采集器：`useSessions((s) => s.jobsBySession[sessionId])`，`null` = 列表不可用，`[]` = 没有任务。

本 Worker 的 worktree 快照 `cf40933` **早于**上面那次提交，所以 `src/client/lib/contract/types.ts`
里还没有这个字段；按主 Agent 的指示，本部件**没有改共享层**，而是在 `index.ts` 里用一份同形的
局部声明 `JobEntry`（逐字段与上面的权威声明一致）读取与标注示例数据。集成后共享字段生效，
`render` 走的仍是 `jobsOf(value: unknown)` 的逐字段收窄，因此有无该类型声明都能编译、都能容错
（旧/新 sessions 服务、字段缺失都不会让 selector 抛错）。

| `stats.jobs` | 卡片 |
| --- | --- |
