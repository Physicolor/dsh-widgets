# sys-power — 供电

## §0 审计（V3 §0 六问，动手前逐条回答）

**Q1 · 这个信息是不是已经在别处更方便地展示了？**
Windows 自己的任务栏托盘图标就在常显电量与"剩余 xx"，所以本卡**不重复那个百分比本身**，它重复的是"这件事在 agent 仪表盘上可见"：
- 产品自身 UI（输入框、页头、设置页、rail 之外的一切）**没有**任何供电读数 → 不算"别处已展示"；
- 任务栏在专注场景下常被全屏窗口遮住，而本卡与 token / 工具 / 后台任务同屏 —— 车主真正要防的是"长跑跑到一半掉电"，那是**同一屏上的相关性**，任务栏给不了。
判定：**保留**。重叠只发生在"百分比"这一个数上，且本卡用环 + 电池图标 + 来源词把它固定在"硬件供电"的语境里。

**Q2 · 有没有功能高度重合的既有组件？**（窗口 / 范围 / 单位 / 时态 四栏逐条比）

| 既有组件 | 窗口 / 范围 | 单位 | 时态 | 与「供电」的差异 |
| --- | --- | --- | --- | --- |
| `sys-cpu` | `/api/sysinfo` 瞬时采样 · 单机 | `%`（或 GB） | 瞬时 | 语义是"机器**忙不忙**"（越高越坏）；本卡是"机器**还能不能跑**"（越低越坏），且数据源是 `/api/host/overview` 而不是 sysinfo |
| `sys-rings` | 同上 · CPU + GPU 两环 | `%` | 瞬时 | 同上的性能族；本卡的环只画电量这一个"越低越坏"的量 |
| `sys-board` | sysinfo 汇总面板（CPU/内存/GPU/VRAM） | `%` / GB | 瞬时 | `SysInfo` 里**没有** power 字段，供电不在其中 |
| `sys-disk` | 各盘容量 | GB / `%` | 瞬时 | 磁盘剩余与供电无交集；但它是本仓 **`fmtUptime` 先例**的出处（见 §4） |
| `sys-gpu` / `sys-gpu-line` | GPU 性能 / 显存 / 温度 | `%` / GB / `°C` | 瞬时 | 性能族 |
| `usage-mix` / `quota-manage` / 会话类 | token 与套餐额度 | token / `%` | 滚动窗口 | 与硬件无关 |
| `cache` / `tool` / `tokens` | 会话内投影 | token / 次 | 会话累计 | **版式基准**，不是功能重合 |

全仓 44 个部件里**没有任何一个**读 `stats.host`（`grep 'host?\.' src/widgets` 只命中本卡）——`/api/host/overview` 的 `power` 切片在此之前没有消费者。判定：**无重合，不合并**。

**Q3 · 不读文档，用户怎么分清它和 `sys-rings`（都印百分比）？**
三处自己回答"我是哪个"：名字「供电 / Power」；大数字永远带**电池环 + 电池图标**（`headRing.icon: 'battery'`），而 `sys-rings` 的环里没有图标、环下标着 CPU / 内存 / GPU；灰字第一句是**电源来源**（`插电` / `电池` / `台式机（无电池）`），不是负载名。

**Q4 · 这个大数字是什么单位、什么范围、什么时间点？**
`0`–`100` 的整数百分比，单位 `%`，时间点 = host 最近一次采样的时刻（sys 家族同一 tick，缺省 10s，与 `/api/sysinfo` 同一次快照）。它回答"**此刻**这块电池还剩多少"。范围 0–100；`0%` 是真实读法而非空态；没有读数时**不画大数字**（见 §4/Q5），所以卡面上不会出现需要解释的占位符。

**Q5 · 它应该一直在，还是可以消失？**
`builtin: true` 但 `defaultInstalled: false` —— 用户**主动装进 rail**，所以装完就不许再"突然出现/消失"。规则：
- **只有** `stats.host?.power === null`（整块供电数据不可用：没有电池**且** `powercfg` 没答，或路由还没回）→ `render` 返回 `null`；
- 其余**全部**状态都渲染，包括"无电池（台式机）"——它走**安静形态**（无环、无大数字、灰字写明「台式机（无电池）」），而不是隐藏自己。
这正是 V3 §0.5 要求的"缺数据显示安静空态，不要隐藏"；V3 §1.6 也点名了 `percent === null` 要"走安静的无电池形态"。

**Q6 · 颜色有没有被赋予一个用户能说出的含义？**
绿/黄/红**只表示等级**，本卡只启用两档，且都能一句话说出：

| 颜色 | 触发 | 用户能说出的话 |
| --- | --- | --- |
| 琥珀 | 用电池且 `10 ≤ percent < 20` | "电量低到可能让长跑中断了"（20 是 Windows 自己弹低电量提示的线） |
| 红 | 用电池且 `percent < 10` | "马上就要断了" |

**不染色**的量（一律默认前景色）：电源来源、电源方案、剩余时长、20% 及以上的电量、插电中的电量（哪怕在充电）、以及"来源不可知"的电量 —— 后者不是"正在放电"的证据，染琥珀就是无根据地报警。`—` 用 `muted` 灰是"缺读数"的语言，不是危险的语言。

**对比过的既有组件**：`sys-cpu`、`sys-rings`、`sys-board`、`sys-disk`、`sys-gpu`（含 `sys-gpu-line`）、`cache` / `tool` / `tokens`（版式基准）、`usage-mix` / `quota-manage`（确认与额度无关）。

## 1. 这张卡回答什么问题

**「这台机器现在是插电还是用电池？还有多少电、还能撑多久？跑的是哪个电源方案？」** —— 一句话：长任务被中断的最常见原因之一（拔电降频 / 电量耗尽休眠），在卡面上提前看见。

## 3. 数据来源

只读 `stats.host?.power`（契约 `HostPower`，来自 host 路由 `/api/host/overview`）：

```
HostPower = { onAc: boolean | null, percent: number | null,
              minutesLeft: number | null, scheme: string | null }
```

口径与**明确不属于本卡的两件事**：

- **Win32 哨兵不由本卡处理。** `EstimatedRunTime = 71582788`（0x4444444）表示「交流电 / 未知」，host 的 `toPower()` 已经把它折成 `null`。本卡只判断 `null`，文件里没有任何哨兵常量——两处都判断会让「到底谁负责」变成猜谜。
- **电源方案不映射。** `powercfg` 打印的是本地化字符串（`电源方案 GUID: … (平衡)`），host 已剥掉前缀只留括号里的名字。本卡**原样印**（`平衡` / `Balanced`），不做中英对照表：自己映射就会和机器「设置 → 电源」页上写的字不一致。
- `percent` 来自 `[int]$b.EstimatedChargeRemaining`；`minutesLeft` 只在**放电且 runtime > 0** 时非空。
- `onAc` 的语义是 host 折出来的 `BatteryStatus === 2`，即「**交流电（充电中或已满）**」——所以插电充电中的笔记本（如 63%）也印「插电」，且不染色。契约里没有「充电中」这一位，本卡不假装有。
- 有环时大数字来自 `headAfter.big`，`value` **留空**（契约硬规则：环头的大数字只有一个来源，否则同一个数会印两遍）。

几种「空」在本卡各有所指：

| 情况 | 结果 |
| --- | --- |
| `stats.host` 为 `null` / `power` 为 `null`（没有电池**且** `powercfg` 没答） | `render` 返回 `null`，整卡不出现 |
| `percent === null` 且 `onAc === true`（台式机 / 无电池读数） | **无环、无大数字**；legend「台式机（无电池）」；明细只剩电源方案 |
| `percent === null` 且 `onAc === false`（有电池但读数缺失） | **无环、无大数字**；legend「电池 · 电量未知」 |
| `percent === null` 且 `onAc === null` | **无环、无大数字**；legend「供电未知」（不再叠一句"电量未知"） |
| `minutesLeft === null`（插电，或电池没给估算） | **整行不显示**（不是 `—`） |
| `scheme === null`（`powercfg` 没答） | 该行印 `—` + `tone: 'muted'`（这是一次**失败的读取**，值得显示） |
| `0%` | 正常渲染 `0%` + 空环（**不是**空态；`0` 与"没有读数"是两句不同的话） |

## 4. 元素为什么这么摆

- **大数字在标题正下方（`headAfter.big`，不是 `value`）**：这是本仓库唯一写法的头部阶梯（蓝 13px 标题 → 20px 数字 → 灰 10px caption）。用 `value` 会被推进正文，在有 `headRing` 的卡上还会变成第二个来源（`CardBody` 注释里写明环头的数字只能来自 `headAfter.big`）。
- **右上角电量环（`headRing`）= 车主本轮的要求**：`ratio = percent / 100`、`icon: 'battery'`、`label` 放精确百分比（环心画不下字，精确数走 hover）。环与 20px 数字是同一个读数的两种语言，不是两个读数。环的 `tone` 与数字的 `valueTone` **同一个来源**（`powerTone()`），所以"低电量变琥珀"在环和数字上同时成立，不会一个变色一个不变。
- **灰字只留「来源」（本轮的消重决定）**：V3 §1.6 给了两个方向，本卡选**灰字=来源、明细=方案**。理由：来源是这张卡的主角（"这台机器还能不能跑"取决于它），它值得留在更醒目的 caption 位置；方案是次要的机器设置，放明细行。于是：
  - 旧 `供电 交流电` 行 **删除**（灰字已经在说来源）；
  - 灰字里的 `· 平衡` **删除**（方案只在明细行出现一次）。
  一个读数只印一次，卡面因此从"3 行 + 一句重复"变成"1–2 行 + 一句来源"。
- **「剩余」行不是占位符（本轮的车主决定）**：插电时 Windows 根本不报续航，一行 `—` 会被读成"这个读数坏了"，而它只是**不存在**。所以 `minutesLeft === null` 时整行不画——本卡唯一允许改变行数的行。反例留在明细里：`scheme === null` 是**读取失败**，仍然印 `—`，因为那里"本来应该有一个值却没有"。
- **续航写成 `2h14m` 而不是 `fmtDuration` 的 `134m0s`**：`fmtDuration` 是会话**秒表**词汇（`45.2s` / `2m42s`），把 host 给的 134 分钟印成 `134m0s` 等于让读者自己做一次系统已经做过的除法。续航估算与隔壁 `sys-disk` 的进程 uptime 同族，所以本卡抄它的 `fmtUptime` 形状（`2h14m` / `41m`），理由也写在同一条注释里。**这是本轮从 PNG 里看出来并修掉的问题**（见 §9 的验收记录）。
- **无电池时不画大数字**：`—` 在 20px 主色下会被读成"涂黑条"（契约里 `valueTone: 'muted'` 就是为它加的），而车主本轮明确"不要 `valueTone`"；把不存在的读数用 20px 画出来更违背"没有数据就不出现"。所以安静形态**根本没有大数字**，靠灰字「台式机（无电池）」把话说完。
- **明细贴底（`bodyAnchor: 'bottom'`）**：`headAfter` 一行会让头变高，默认（`'top'`）会把明细顶到 caption 下面、把空白留在卡底。贴底后空白落在头与明细之间，明细在卡的地板上——与「会话 Token / 缓存命中 / 工具调用」完全同一姿态。
- **高度预算实测**（与 `card-geometry.ts` / `CardBody.tsx` 对账）：`pad 15 × 2` → 头（标题 16 + 4 + 数字 25 + 2 + 灰字 12 = 59；环 52 比它矮，不改变头高）+ 明细（1px 上边线 + 6 上间距 + N 行 ×12 + (N−1)×4）。**2 行 = 124 / 150，1 行 = 112 / 150**（即便加回第三行也才 140，不溢出）；本卡按消重后的 3 个事实固定输出 1–2 行。
- **灰字旁边的环不会挤掉文字**：环 52 + gap 8 → 左列 ≈ 60px。有环时灰字最长是「供电未知」（4 字 ≈ 40px），实测不截断；最长的「台式机（无电池）」只出现在**无环**形态（左列满宽 120px），所以它也不会被省略号吃掉（PNG 已逐张确认）。

## 5. 语气方向（本卡自己定，写死在 `index.ts`）

| 阈值常量 | 值 | 语气 | 依据 |
| --- | --- | --- | --- |
| `WARN_PERCENT` | 20 | `valueTone: 'warn'` + 环/图标琥珀 | Windows 自己就是在这个电量开始弹低电量提示，卡与系统同一口径，不另立标准 |
| `DANGER_PERCENT` | 10 | `valueTone: 'danger'` + 环/图标红 | 电量即将成为长跑被中断的原因 |

**方向与「越高越坏」的邻居卡相反**：本卡是「低才坏」（越低越危险），且**只在放电时染色**：
`onAc !== false`（含 `onAc === null`）一律不染色——「来源不可知」不是「正在放电」的证据，染琥珀就是无根据地报警。
`percent === null` 不染色也不画环（没有读数就没有判断）。
健康电量（20% 及以上）与插电中的电量**不给 `valueTone` 键**（不是给 `'primary'`）：没有等级就不写等级。

不染色的地方：来源、电源方案、剩余时长的明细行不染色；失败读数的 `—` 用 `muted`（灰），这是"缺读数"的语言，不是"危险"的语言。

## 6. 配置项

**无。** 本卡不提供 `configSchema`（规格书未要求）。刷新节奏因此走 sys 家族的统一默认：任何 `source: 'sys'` 的实例被装上后，采集器按该实例的 `interval` 配置取**最短**值轮询，缺省 **10s**（`resolveInterval(undefined) → 10`，`/api/sysinfo` 与 `/api/host/overview` 同一次 tick）。若车主希望像 sys-cpu / sys-rings 那样选 5/10/30/60s，加一行 `configSchema: intervalSchema()` 即可（共享层已有，无需新增原语），但那多一个配置项，本卡按规格书没加。

## 7. 空态 / 降级行为

- `stats.host === null` 或 `stats.host.power === null` → **`render` 返回 `null`**（整卡隐藏）。理由：`power` 为 null 只有在"没有电池**且** `powercfg` 也没答"时才会发生，此时这张卡没有任何一句话是真的。
- 「剩余」行在 `minutesLeft === null` 时**不存在**（不是 `—`）：插电时系统本来就不报剩余续航，一个不存在的读数不该占位（车主原话）。唯一保留的说明是 `cardHint`，而且只留给**最含糊的那一种**（用电池、电量已知、但系统没给续航估算）：`系统没有报告剩余续航估算值，因此本卡不显示「剩余」这一行`。插电态与无电池态不挂 hint——前者自明，后者灰字已经说明。
- 明细**至少一行**：电源方案永远在（读失败时 `—` + `muted`），所以卡不会出现空图表。
- `sim` 优先于实时数据：预览要能走遍 5 个状态，而实时数据无法按需制造"低电量"。

## 8. 与既有卡的差异

全仓 44 个部件里**没有任何一个**读过 `stats.host` —— 最接近的邻居是 sys 家族（见 §0/Q2 的四栏对照表）：

| 卡 | 读什么 | 与本卡的关系 |
| --- | --- | --- |
| `sys-cpu` / `sys-rings` / `sys-gpu` / `sys-gpu-line` | `/api/sysinfo` 的 CPU / 内存 / GPU | 都是**性能**读数；本卡是**供电**读数，两者是"机器累不累"与"机器还能不能跑"的区别 |
| `sys-board` | sysinfo 的汇总面板 | 不含供电（`SysInfo` 里没有 power 字段） |
| `sys-disk` | 磁盘容量 | 硬件读数，但对象不同；本卡复用的是它的 `fmtUptime` **形状**（不是数据） |
| `quota-manage` / `usage-*` | 套餐额度 | 与硬件无关 |
