## 1. 这张卡回答什么问题

**"这台机器还有地方可写吗，以及 harness 自己在吃掉多少？"**

长跑的失败往往不是模型出错，而是两种运维事故：**盘满**（系统盘低于约 10% 时 Windows 明显降速并开始拒绝更新）与**会话日志膨胀**。既有的 44 张卡全部在回答"用了多少 token / 花了多少钱"，没有一张回答"跑它的这台机器还活着吗"。

## 3. 数据来源

只读 `stats.sysinfo.machine`（`MachineInfo`；host 侧 `src/host/machine.ts`，磁盘 30s、会话目录 60s 各自 TTL）：

| 字段 | 口径 | 卡面上的位置 |
| --- | --- | --- |
| `disks[].mount` / `total` / `free` | `fs.statfs` 字节数（`free = bavail × bsize`），只含真实存在的固定盘，按盘符序 | 横条（一条一盘）＋行标签（左）＋右端已用 % |
| `home.sessionsBytes` | `$DSH_HOME/sessions` 递归文件大小之和（字节） | 灰字（`345M`） |
| `home.recentFiles` | 其中 mtime 在**最近 1 小时**内的文件数（增速信号） | 灰字（`+13`） |
| `home.sessionsFiles` | 上述递归文件数 | **悬停**（`cardHint`，原因见 §4.4） |
| `proc.pid` / `rss` / `cpuPercent` / `uptimeSec` | `dsh web` 进程自身（RSS 字节；CPU 为两次采样间的增量，**首个样本为 null**） | 悬停；`home === null` 时占那一行灰字 |

**推导全在本目录内**（`index.ts`），没有往共享 `lib/` 加任何东西。

### 3.1 为什么自己写 `fmtBytes`（没有复用 `fmtTokens`）

`src/client/lib/format.ts` 的 `fmtTokens` **顶上只有 M**：652 GB 会被打成 `667648M`；它的"3 位有效数字"规则也是为 token 计数挑的，容量要到 G/T 才有意义。所以本地 `fmtBytes` 用 K/M/G/T（1024 进制，与 sys 家族的 `fmtGb` 同一约定），规则是 **<100 保留一位小数、≥100 取整**（`63.0G` / `300G`）。`fmtUptime` 同理不复用 `fmtDuration`（会把 3h54m 打成 `234m0s`）。

### 3.2 单位是 1024 进制，标签写 G

`fs.statfs` 报原始字节；÷1024³ 得到的其实是 GiB，但仓库既有的 `fmtGb`（sys-cpu / sys-gpu-line 在用）就这么标注，**同一栏里的两张卡不能对"G"有两种解释**，所以跟随现状。

### 3.3 `pct` 是"已用"，`label` 是"剩余"

`quotas.pct` 在这些原语里是**填充比例**——条填多少，右边就印多少。所以 `pct = usedPct(free/total)`（条 = 已用），**文字侧（行标签）= 剩余字节**。旧版传 `ratio: free/total`（条 = 剩余）是反的，已在修订版 2 删除。

### 3.4 中点 `·` 的用法（本版统一）

灰字与标签里的 `·` 一律读作"并且"：`DSH 会话日志 345M · 近 1 小时 +13 个文件` = 体积 **并且** 增速。两个读数各自自解释，中间不需要连接词。

## 4. 元素为什么这么摆（修订版 3 的四条意见逐条对应）

**这张卡是"量出来的"。** 2×4 = 312×150 外框、内间距 12 → 内容区 **286 × 126**。下面每个数字都是 gallery 真浏览器实测（探针见 §9）。

| 块 | 修订版 2 | **修订版 3** |
| --- | --- | --- |
| 标题行 | 16 | 16 |
| `headAfter` 行（大数字 20px） | 4 + 25 = **29** | **0（删除）** |
| 灰字 | 2 + 12.5 = 14.5（两行压在 25px 行框里） | **2 + 14 = 16**（`legend` 一行） |
| 头部合计 | **59.5** | **30.5** |
| 图表（2 盘） | 47.7（行高 21.3 × 2 + 5 行距） | 47.7（未变，见 §4.3） |
| 图表距卡底 | 1 | 1 |
| 头部与图表之间的空隙 | 60.3（其中 31.3 由 `marginTop: auto` 撑出） | **60.3（其中 44.3 由 `marginTop: auto` 撑出）** |

（"头部与图表之间的空隙"两版相同，是因为图表**贴底**：头部收短的 29px 全部变成了那块空隙。这正是 §4.8 的那个空白。）

实测卡片 `clientHeight = scrollHeight = 148`，**无溢出**（`CardBody` 的 tile-fits 守卫没有标红）。

### 4.1 大数字 `D: 剩余 62.9G`：**删除**

车主："大文字 `D: 剩余 62.6G` 和下面的文字信息相同，直接删掉。"

确认属实：卡上原本有两处印同一块盘的剩余量——20px 的 `D: 剩余 62.9G`（`headAfter.big`）与它下面第一行的 `D: 剩余 62.9G / 652G`（`quotas[0].label`）。按"一个读数只出现一次"，**删掉大数字那一处**，保留行（行还多给了分母，信息量更大）。

实现上不是"把字改空"，而是**整行不存在**：不再返回 `headAfter`，也不再返回 `value`（`value` 会把同一个读数推进正文，等于换个位置复发）。`valueTone` 随之删除——大数字是它唯一的消费者。

**顺带修掉的一个副作用**：等级红以前同时出现在大数字与危险档的条上（"一个阈值、两处颜色"）。现在只剩条，这条卡不可能自相矛盾。

### 4.2 灰字：从"两行压行框"改为**一行 `legend`**

车主："`DSH 会话日志 357M 近 1 小时新增 25 个文件` 在蓝色标题下方一行刚好能放下。"

- 用 `legend`（契约里就是"标题正下方的一行小灰字，不参与垂直对齐"），**不是** `headAfter.smallLines`——后者是压在大数字 25px 行框里的两行块，大数字没了它就没有宿主。
- 文案：`DSH 会话日志 {size} · 近 1 小时 +{recent} 个文件` / `DSH session logs {size} · +{recent} files this hour`。
  **为什么是 `+13 个文件` 而不是 `+13`**：修订版 2 的 `+13/h` 曾被车主判为读不懂——它可以是文件、字节或会话数。本版把单位写死在数字后面（`个文件` / `files`），前面那句 `近 1 小时` / `this hour` 说明窗口，句子自解释。`+` 只表示"新增"。
- **降级分支同一句式**：`home === null`（会话目录读不到）时整行换成 `dsh web 进程内存 {rss} · CPU {cpu} · 已运行 {uptime}` / `dsh web memory {rss} · CPU {cpu} · up {uptime}`——同样是"是什么 · 什么状态"。**绝不印文件数**（那会被读成"0 个文件"）。

### 4.3 图表：仍然是 `kind: 'quotas'`，并且**这已经是既有能力下的最大尺寸**

车主："把下面的大部分空间留给柱状图，可以让柱状图和文字稍微大一点点。"

**先说结论：空间确实全部留给它了，但"变大"这一步在共享渲染器里被写死了，部件侧做不到。** 证据与提案如下。

读过 `render/charts/` 里两个候选的实现（不是猜）：

| 原语 | 实现事实 | 判定 |
| --- | --- | --- |
| `bars`（`bars.tsx`） | **竖直**柱：柱区高 `56 × scale` 写死，柱宽 60%，唯一的文字出口是**柱下**的 9px 标签 | ✗ 结构上竖直；改成横排要动共享渲染器 |
| `barsV`（`barsV.tsx`） | 同样竖直，且高度写死等于热力图内容高 | ✗ 同上 |
| **`quotas`（`quotas.tsx`）** | **每行：标签左 + 百分比硬右 + 24 格分段条在下一行**；行内三个尺寸是**字面量 × 卡片 scale**：标签 `9 × scale`、条高 `9 × scale`、格间隙 `2 × scale`、行距 `5 × scale` | ✓ **就是"横板"**，且车主认识这个形状 |

`scene` 里 `scale = unit / BASE_SIDE`，而 `unit` 就是**卡片的基准边长**（2×2 与 2×4 都是 150），所以 **scale 恒等于 1**，行高恒等于 21.3px。部件能传的只有 `chart` 自己的数据（行数、标签、百分比），`ChartProps` 的 `side`/`width`/`pad`/`scale` 四个值对 `quotas` 的行内尺寸**没有任何影响**——只剩一个 `scale` 能改，而它同时会改掉标题、大数字与卡片内边距，那不是"让图表变大"，那是"把整张卡放大"。

所以本版做到的是**既有能力下的最大**：

1. 头部从 59.5px 收到 30.5px，**腾出的 29px 全部落在图表上方**（`gapHeadToChart` 从 60.3 里属于自动外边距的部分由 31.3 变 44.3，图表本身仍然贴底、与邻居共享底线）；
2. 图表拿到的是卡内**全部剩余高度**：内容高 126 − 头部 30.5 − 间距 6 = **89.5px 是卡身的预算**，2 盘只用 47.7px（余 41.8），3 盘用 73.9px（余 15.6），都不会撑高卡片；
3. 行数上限仍是 3（4 行 = 4×21.3 + 3×5 = 100.2px > 89.5px，会把卡片顶破网格行，`CardBody` 的 tile-fits 守卫会标红）。

**共享层提案（要"再大一点"只差这一个字段）**：

```ts
// src/client/lib/contract/types.ts — WidgetChart
/** 每行的相对高度/字号倍率，默认 1（现行为）。
 *  `quotas` 用它把"标签行 / 条高 / 行距"一起缩放：
 *  `1.25` → 标签 11px、条 11px、行 24.6px。 */
density?: number
```

- **接在谁身上**：`WidgetChart`（`quotas` 与 `bars`/`barsV` 都是固定尺寸的图表，谁需要谁传）。
- **渲染器改哪一行**：`src/client/render/charts/quotas.tsx`
  - L17 `const cellH = Math.max(5, Math.round(9 * scale))` → `Math.round(9 * scale * d)`
  - L38 `gap: Math.round(2 * scale)` → `Math.round(2 * scale * d)`
  - L40–41 两处 `fontSize: `${Math.round(9 * scale)}px`` → `* d`
  - L46 `gap: Math.round(5 * scale)` → `Math.round(5 * scale * d)`
  - （`bars` 若要一起受益，L10 的 `h` 与 L29 的 `fontSize` 同理。）
- **期望的视觉效果**：`density: 1.25` 时标签 9→11px、分段条 9→11px、行距 5→6px，行高 21.3→**24.6px**；3 行 73.9→**83.8px**，仍小于卡身预算 **89.5px**（本版头部收短后的实测值），**不会溢出**。
  取 11px 而不是 12px 的理由：11px 是本仓库明细行字号（`breakdown` 用 `10 × scale`、`figures` 的标签 9、卡片灰字 10），跨过 12px 会让磁盘行**看起来像标题**，而它只是明细。
- **本卡要传的值**：`density: 1.25`。
- 若主 Agent 更倾向于"按可用高度自动分配"，等价方案是给 `ChartProps` 加 `height?: number`，由 `CardBody` 传卡内剩余高度；但那样 `quotas` 的行为会随卡片内容变化，而仓库目前的图表都是**确定尺寸**（`segments` 的注释里明确写了"content sizes the card"），所以我推荐显式 `density`。

**这条提案落地前，本卡不为了"看起来更大"而改语义**：不换成 `figures`（那是 label-over-value 的两列文字，没有条）、不换成 `bars`（竖直）、不重复数据。

### 4.4 会话日志的**文件总数**为什么在悬停

它是这条线里**唯一无界**的读数（`345M` 与 `+13` 受机器容量约束，文件总数会到五位数）。灰字是单行 `nowrap` + ellipsis，五位数会开始挤；本版实测最长的灰字是降级分支的中文 `dsh web 进程内存 525M · CPU 2.1% · 已运行 3h54m` = **242.3px**（行宽 286px，余 43.7px），线上分支只有 199.6px（中）/ 207.3px（英）。把总数留在卡上会立刻吃掉这 43.7px 的余量。

### 4.5 行数上限 3 与排序：**最紧张的排最前**

`MAX_ROWS = 3`。`sort` 是稳定的，数值相等时保持盘符序，不会在两次 10s 轮询之间换来换去。被折叠的盘写进悬停：`另有 1 块盘空间更充裕：E: 剩 373G`。

本版删掉了"哪块盘是头条"的那次挑选（大数字是它唯一的消费者）：排序后的 `shown[0]` **就是**最紧张的那块，上限因此仍然不可能藏起危险盘。

### 4.6 贴底由**契约规则**保证，不再写 `bodyAnchor`

修订版 2 显式写了 `bodyAnchor: 'bottom'`。本版**删掉**——`CardBody` 的判据是 `out.headAfter !== undefined && out.bodyAnchor !== 'bottom'`，而本卡已经没有 `headAfter`，foot 天然是 `marginTop: auto`。所以：

- 语义正确（贴底）；
- 少一个"看起来在起作用、其实不起作用"的字段（实测：加上它前后 `clientHeight` 与 `scrollHeight` 完全相同，`mt` 都是 44.3125px）。

### 4.7 右端百分比为什么是整数、为什么**向上**取整

档位判据是 `free < 10% / 20%`，而印出来的是**已用**。`Math.ceil` 的已用比例**永远不会夸大剩余空间**（告警该有的方向），并且让数字和颜色落在 90% 线的**同一侧**：红档 ⇔ `free < 10%` ⇔ `used > 90%` ⇒ 印出的已用 ≥ 91；黄档 ⇒ ≤ 90。另加 `1e-6` 守卫：恰好 90.00000000000001%（二进制浮点）不能被印成 `91%`。

### 4.8 2 块盘时中间那一大块空白：**故意的**

本版删掉大数字后，头部只占 30.5px，图表仍然贴底且仍是 47.7px，于是**中间空出约 44px**。

- **不放东西**：加回任何一行就是加回"一个读数只出现一次"的违规，或把悬停里的信息搬上来（悬停的存在理由正是卡面没有像素）。
- **不改成顶对齐**：`store` 里试过 `bodyAnchor: 'top'`，实测**没有任何变化**（`headAfter` 缺席时 `CardBody` 的 `headAnchorsTop` 恒为 false，见 §4.6），所以那是死字段而不是备选方案。
- 这个空白是**共享渲染器尺寸写死的直接后果**（§4.3）；`density` 一落地，空白立刻变成更高的条。

### 4.9 历史存档：修订版 2 的三条决定

保留原因：这一版推翻的正是其中两条，理由必须可查。

1. **大数字（`D: 剩余 62.9G`）**："剩余"这个单位词是修订版 2 加的（防止裸数字被读成"已用"）。本版删除整行，问题消失。
2. **两行自解释灰字**（`DSH 会话日志 345M` + `近 1 小时新增 13 个文件`）：修订版 2 用 `smallLines` 压在 25px 大数字行框里，**零额外高度**。这个理由在本版失效——它赖以生存的那一行被删了，所以改为单行 `legend`（16px）。
3. **`bodyAnchor: 'bottom'`**：修订版 2 需要它，因为 `headAfter` 会把 body 改成顶对齐。本版没有 `headAfter`，字段成为死字段，删除（§4.6）。
4. **`MAX_ROWS = 3` 的原始测算**（当时假设可用 79px）：3 行 74 ≤ 79、4 行 100 > 79。本版续用该上限，并在删除大数字后重新测过（3 盘时 3 行 73.9px ≤ 95.5px 可用）。

## 5. 语气方向

**由本部件定义，绝不让渲染器猜**：判据是**剩余**空间，越少越危险——与 利用率（sys-cpu / sys-gpu / sys-rings）**极性相反**。条是**已用**画的，所以两句话是同一件事：`free < 10%` **就是** `used > 90%`，警报条是**满**的那根。

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `FREE_DANGER` | `0.10` | Windows 在系统盘剩余低于约 10% 时明显降速，并开始拒绝更新 / 服务包 / 卷影副本——不是审美阈值 |
| `FREE_WARN` | `0.20` | 还来得及"计划清理"而不是"抢救"的那一档 |

- 条的颜色 = 档位（`quotas[].tone`：danger / warn / primary）；`primary` 是**中性品牌色**，不代表"好"。
- **本版起颜色只有这一个出口**（大数字与 `valueTone` 已删除）：一个阈值，一处呈现。
- **没有染色**的量：会话日志体积、新增文件数、进度百分比。它们没有等级含义。

## 6. 配置项

**无。** 刷新节律由壳统一管（已装 `source: "sys"` 的卡取最短间隔，缺省 10s；host 侧磁盘 30s / 会话目录 60s 各自 TTL），卡面上没有需要用户选的口径。不加"为了有配置而存在"的配置项。

## 7. 空态 / 降级行为

| 情况 | 行为 | 理由 |
| --- | --- | --- |
| `sysinfo` 缺失 / 非对象 / 老 host 没有 `machine` | `render` → **`null`** | 契约里 `skeleton` 的注释写明：加载骨架是**壳**的职责——widget 分不清"还在飞"与"答了但为空"。本卡不返回骨架 |
| `disks` 为空 / 全部 `total <= 0` | **`null`** | 卡片的前提（这台机器有固定盘）不存在 |
| 个别盘 `total` 非有限值或为 0 | 丢这一条，其余照画 | 无法计算占比，画成 0% 条是编造 |
| `home === null`（会话目录读不到） | 灰字换成 **web 进程**：`dsh web 进程内存 525M · CPU 2.1% · 已运行 3h54m` | `home === null` ≠ 空目录。**绝不**印文件数（那会被读成"0 个文件"） |
| `proc.cpuPercent === null`（host 首个样本无增量） | 该处印 `—` | 契约的 `null` 语义；不写成 0.0% |
| `home.recentFiles` 为 0 | 正常印 `+0 个文件` | 这是真实读数（最近一小时没有写入），不是缺数据 |
| 固定盘 > 3 块 | 只画**最紧张的 3 块**，其余进悬停 | §4.5：绝不顶破网格行，也不藏起最紧张的盘 |

**预览专用状态**：`example.simSteps` 两态（`noHome: false / true`），点击卡片切到"会话目录读不到"的降级形态；`sim` 是 `simSteps` 的第一项。`meta.sim` 只由预览通道传入，**rail 只传 `{ size }`**，线上不受影响。

**接线骨架（`manifest.skeleton`）**：`{ "shape": "quotas", "count": 3 }`——卡身是堆叠的额度行，骨架必须长得像它自己（V2 §3）。**本版没有改骨架**：形状与行数都没变（变的只是头部高度）。

## 8. 与既有卡的差异 / 遗留

**不重复**：既有卡（含 sys-cpu / sys-gpu / sys-rings / sys-board / sys-gpu-line）读的都是 `/api/sysinfo` 的**硬件半边**（CPU / 内存 / GPU），这张卡读的是 `machine` 半边（盘 / 会话日志 / 宿主进程）。`grep machine` 在本仓库源码里除 host 采样器与契约类型外没有别的消费者。

**取舍与遗留**：

1. **2 块盘时头部与图表之间约 44px 空白**（§4.8）：不是排版失误，是"图表行高写死在共享渲染器里"的直接后果。`density` 落地即消失。
2. **左右两个量不同**：左 = 剩余（车主要求），右 = **已用**（原语只给这一个文字出口，且它必须等于填充比例——`quotas.pct` 就是填充比例）。行结构因此是官方额度行的样子：左边说是什么，右边是条自己的读数。
3. **`home.sessionsFiles` 在悬停**（§4.4）：单行灰字放不下第三个无界读数。
4. **没有做点击/动作**：卡面不可点击（不占用 `cycle`），也没有 `corner` 按钮。
5. **需要共享层补的东西：有，一个**——`WidgetChart.density?: number`（§4.3 给了字段、文件、行号与期望像素）。落地前本卡在既有能力内已是最大。
