# heatmap-bars-wide — 用量柱状图（2×4，近 30 天）

`heatmap-bars` 的宽版：窗口 30 天，**每根柱两天**（15 根），版式按仓库既有的宽卡惯例排。

## 卡面

```
用量柱状图            MAX 35.9M  TOTAL 254M   ← 蓝色标题（左） + 两个带标头的读数（右，10px 灰）
▇▅▃▆▂▇▄▃▅▇▂▆▄▅▇                               ← barsV：每根柱 = 2 天，最早→最新
8.31                                  9.28    ← 每端一个短日期：该柱「结束于」的那天（右端 = 今天）
```

- **15 根柱**：`lastNDays(raw, 30)` 之后按 `DAYS_PER_BAR = 2` 折叠（共享纯函数 `lastNDays` + 本目录的 `foldBars`）；每根柱的 `ratio` 按**本窗口最重的柱**归一，最重的那几天顶格。
- **柱的标签是单日期**：一根柱 = 两天，标签取它**结束**的那天 —— 两角永远是一个短日期（写成 `8.30–8.31` 会溢出卡片内边距），右端永远是「今天」（与 7 日卡的滚动窗口一致）。分桶这件事由卡片自身的 hover 文案说明（`cardHint`：每根柱 = 2 天），因为两角已经没有地方写区间。
- **两个读数带标头**：`MAX`（最高的那根柱 = 最重的两天，与图里最高柱一致）、`TOTAL`（30 天合计）。用拉丁字母而不是「峰值/合计」，是因为夹在两个数字之间的中文词对左右都没有归属感，而字母与 `M` 结尾的数字天然是一组（单位符号的排版习惯）；顺序沿用家族写法：小的窗口数字在左、合计在右。
- **空态**：`heatmapRaw` 缺失、或窗口内每天都是 0 → `render` 返回 `null`。

## 柱宽是算术，不是样式旋钮

`barsV` 的列 = `gap: 4px`（**写死的、不随柱数/宽度缩放**）+ 柱宽 = 列宽的 93%。2×4 的内容盒是 318px，于是柱宽完全由「传几根柱」决定：

| 柱数 | 列宽 | 柱宽 | 墨迹占比 | 观感 |
| --- | --- | --- | --- | --- |
| 30（每天一根） | 6.7px | **6.3px** | 93% | 细针、发挤（上一版，车主否决） |
| **15（两天一根，本卡）** | 17.5px | **16.2px** | 94% | 与 2×2 的柱（~14.6px / 94%）同款节奏 |
| 10（三天一根） | 28.2px | 22.0px（渲染器上限） | 78% | 更空，峰值被抹平更多 |

2×2 卡在 134px 内容盒里画 7 根 14.6px 的柱，渲染器的硬上限是 `21·scale`（≈22px）。所以**「每天一根柱」与「7 日卡那样的柱宽」在 344px 宽里不能同时成立**：30 根日柱必然是 6.3px。要更粗只能减少柱数；两天一根是**仍然够到这个宽度的最细分桶**。`DAYS_PER_BAR` 一个常量即可切回 30 根日柱或 10 根粗柱。

**真正要在保留「每天一根」的前提下变粗，得改共享层**：让 `barsV` 的 gap 由柱数推导（或由 chart 传入）。就算 gap 降到 1px，30 根日柱也只有 8.7px，仍细于 2×2 —— 这属于船长的选择，不是部件能定的。

## 头部：为什么数字在标题行右端（不是标题下方）

这不是为了塞空间，是仓库对宽卡已经写下的规矩，两个家族逐字相同（同一串数字，只换位置）：

| 位置 | 代码 |
| --- | --- |
| 用量热度图 | `src/widgets/heatmap/index.ts`：`...(wide ? { headRight: figures } : { legend: figures })` |
| GitHub 提交日历 | `src/client/families/github/renders.ts`：`...(wide ? { headRight: label } : { legend: label })` |

设计原则：**字号阶梯不动（13px 蓝标题 / 20px 主体数字 / 10px 灰字），动的是排布，排布跟着格子形状走**。方形卡（2×2）横向没地方，三个元素只能竖着码 —— 灰字落在标题下面；宽卡（2×4）同一行的左端放标题、右端放数字，一行说完「这是谁 + 两个数」，头部就只剩一行（≈17px），省下的纵向空间归数据。反过来说，如果宽卡也竖着码三行，它会是仓库里唯一这么做的 2×4 —— 正是被指出的「设计语言不统一」。

本卡没有主体大数字：Token 用量家族（热度图、柱状图）都不印 20px 数字，图表才是内容。高度账：`13 + 17(头部) + 79(barsV 固定绘图区) + 13 = 122 ≤ 160`。

## 和「Token 用量」/ 7 日柱状图的区别

| | 用量热度图（日历） | 用量柱状图（2×2） | 本卡（2×4） |
| --- | --- | --- | --- |
| 横轴单位 | 周 | 天 | **2 天** |
| 窗口 | 2×2 近 3 个月 / 2×4 近半年 | 近 7 天 | **近 30 天** |
| 读数 | 今日 / 窗口合计 | 今日 / 7 天合计 | MAX（最重的两天）/ TOTAL（30 天） |
| 回答 | 作息与强度模式 | 这一周每天多少 | **这一个月哪几天最重** |

## 示例数据（预览）

40 天拟真日志，**窗口内每天都有值**（周末轻、每十天一个高峰）。故意不留空日：muted 短桩在预览里几乎看不见，会让人以为「这张卡只覆盖了 25 天」；空日属于实时数据的真实状态，不属于预览。

## 数据

只读 `stats.heatmapRaw`（机器口径 `Record<'YYYY-MM-DD', number>`，今天的值由采集器实时补齐）。**不读** `stats.heatmapGrid`：它是已经折好的 7×13 日历网格，柱状图要的是逐日序列。无 `manifest.source`：纯同步投影，不存在加载骨架。
