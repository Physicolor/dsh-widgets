## v1.8.2 — the plugin loads on DSH 0.2 again

> A compatibility release. DSH 0.1.7 added a **peer check at install and boot**: a plugin whose declared `@deepseek-ai/dsh-*` peer range does not accept the running runtime is refused outright. This plugin declared `@deepseek-ai/dsh-client-ui-slots: ^0.1.0-rc.6`, which cannot accept `0.2.0-rc.x` (a 0.x minor is a breaking boundary in semver), so every user on the `next` line — and every user of the new desktop build, which ships `0.2.0-rc.x` — was told the plugin is incompatible and never got it loaded. The range now covers both lines, and the support was verified by installing and booting the plugin against real runtimes rather than by reading release notes.

### Fixed — the peer range that locked the plugin out of DSH 0.2

- **Reproduced first, against a clean profile.** `dsh plugin --profile web install` on **0.2.0-rc.2** refused the plugin in exactly the words a user would see: `Plugin dsh-widgets@1.8.1 is incompatible with dsh 0.2.0-rc.2: peerDependencies {"@deepseek-ai/dsh-client-ui-slots":"^0.1.0-rc.6"} …`, then restored the profile and told the user to grant an exact-version exemption by hand. The boot path skipped the bundle with `cannot resolve profile bundle` / `incompatible` in the same run.
- **`peerDependencies` widened to `^0.1.0-rc.6 || ^0.2.0-rc.1`.** A union, not an open-ended `>=`: each line is a boundary this plugin has been exercised against, and the next minor gets its own verification rather than being assumed. `@deepseek-ai/cordis: ^4.0.1` needed no change (0.2.0-rc.2 ships cordis 4.0.4).
- **Verified on both runtimes** with a scratch `DSH_HOME` (the real home was never booted with 0.2, so no Session V4 migration could be triggered): **0.1.7-rc.2** and **0.2.0-rc.2** each install, boot with no skipped bundle, serve the client bundle (`dsh-widgets` present in `__DSH_BOOT__.entries`, `dsx-stats-card` in the payload), register all four slots (`conversation.session.header.utilities`, `conversation.composer.dock`, `conversation.input.overlay`, `settings.section` — each `inject` callback fired), answer the host half (`/api/widgets-state` 200, `/api/sysinfo` 200 with real machine data) and render the **Widgets** settings section, with **no console errors and no failed requests**. The rail inside a live session is the one thing a keyless scratch home cannot show (the session-scoped slots do not mount before a model is configured), so that last step is left to the machine that has one.
- **The supported-range copy followed**: both READMEs' badges and compatibility bullets, and the showcase's kicker, terminal title and JSON-LD `operatingSystem`, now say `0.1.x / 0.2.x` — with `website/verify.mjs` (88 checks) still asserting every hand-written version string against `package.json`, which is what caught the copy the moment the version moved to 1.8.2.

## v1.8.1 — the card waves, one head ladder, and the limits that came back

> A fix-led release that also ships the two card waves committed behind v1.8.0. The registry grew from **40 widget units to 55** (17 added, 2 retired) across three batches — the session and the machine, the device family, cost and the review queue — each fed by a new host channel, and a revision pass reworked nine of the shipped cards to the owner's review. On top of that come the two defects a live rail finally showed: **Command Code's monthly limit disappeared from every card** (three upstream endpoints measured at 14–21 s against one shared 8 s budget), and **two neighbouring ring cards drew visibly different heads** (a rung that comes and goes moved the whole ladder). Every change here was proven by a gate diff or a probe before its baseline was rewritten.

### Added — seventeen new card units (40 → 55)

- **The third batch's four units** (`298cd66`): `usage-mix` (cross-provider quota board), `trajectory-stats` (three-lane shares plus a per-instance big-lane cycle), `heatmap-bars-wide` (30-day bars in 15 two-day buckets) and `peak-pricing-board` (band schedule plus countdown, four pinned-clock preview states). `todo-board` was folded into `task` rather than shipped beside it — same id and order, so an installed `task@2x2` upgrades in place and the market keeps one card named Tasks.
- **Wave 1 — seven cards for what the agent is doing and whether the machine is OK** (`79063f2`): `goal-progress` (goal phase, objective, rounds/max, last change), `guard` (the permission preset in force), `jobs` (background jobs: running, longest, newest), `subagent` (dispatched subagents and how many are resumable), `sys-disk` (disk free plus the DSH session log's size and hourly growth), `window-forecast` (whether the 5h / weekly window hits its cap before reset) and `model-config` (which model route / reasoning effort / preset the agent runs).
- **Wave 2 — the device family, cost, and the review queue** (`cd50a73`): `sys-net` (per-adapter receive/transmit rate from a counter delta, plus the busiest link), `sys-power` (battery vs AC, charge, remaining runtime, active Windows power scheme), `sys-procs` (top processes by working set), `session-cost` (the session's tokens priced through the price table, with the amount's provenance printed beside it) and `github-notify` (the review queue — the one GitHub card that says "someone is waiting on you").
- **`sys-services` — the local dependency board** (`fd66438`): liveness and latency of this machine's key local endpoints (DSH web; Ollama / LM Studio are opt-in and get no row at all when switched off, so an uninstalled runtime cannot raise a permanent "down") plus whether the proxy egress really works — a listening port is not an egress verdict.
- **Two units were retired.** `heatmap-bars-wide` was merged into `heatmap-bars` (`e96acc1`) and `model-config` was dropped (`8be5852`, 324 lines), which is why the registry ends at 55 rather than 57.

### Added — the host channels and the data the new cards read

- **`/api/host/overview`** (`src/host/overview.ts`): network throughput, power source, top processes, local service liveness and proxy egress in one route. It is one route because a single `powershell.exe` spawn already costs ~270 ms of floor (a full pass measured ~1.5 s cold; TCP probes 0.2–0.3 ms per port), so battery + processes + counters + power scheme come from one merged script; `proxy` is stale-while-revalidate and the handler never awaits it, so the route stops blocking on the expensive sections after the first call.
- **The review-queue slice** (`notif=1` in `src/host/github.ts`): GitHub's unread threads with per-reason counts and the newest subject, ETag-aware and authenticated-only.
- **The price-table channel** (`src/host/pricing.ts`, `/api/widgets-pricing`): a READER of `dsh-usage-center`'s stored table (`$DSH_HOME/storages/usage-center/pricing.json`), serving provider scope, effective window, peak windows and provenance (mtime-cached). A missing or unparseable file answers `available: false` — it never falls back to a table this plugin invented.
- **Five session-shape projections** (`src/client/data/session-stats.ts`): `normalizeModelSelection`, `normalizeGoal`, `normalizePermissions` and `normalizeSubagents` read the host projection defensively and DROP unknown members rather than passing them through (the projection's value is `unknown`, and a throwing selector costs every card's data in the slot), keeping `null` ("projection absent") distinct from `[]` ("no children"); `deriveTrajectory` folds settled nodes, running tool calls and the open step timeline into the official Trajectory card's three lanes — in-flight work included, so the card moves while the model is working.
- **The machine half of `sysinfo`** (`src/host/machine.ts`): `createMachineSampler()` reports the fixed disks (`fs.statfs`), the `$DSH_HOME/sessions` total bytes plus the number of files whose mtime falls inside the last hour, and the `dsh web` process's own PID / RSS / CPU / uptime.

### Added — one shared head, value and chart layer

- **The third batch's shared primitives** (`298cd66`): a `breakdown` chart; the donut / `headRing` accessory; the segments tone palette plus value mode; the accent tone (the official model-lane mix, now also read by `lanes.tsx`); the head's type ladder (title / figure / caption builders, so a ring head and a stacked head share one typography); the 42px corner disc; the tile-fits guard (clipped in a preview, grown on the rail, both self-announcing); the value-change figure drop; live-data previews (`buildLiveStats` / `buildPreviewStats`); the capped-arc rule (only 100% closes a ring); `ConfigField.hint`. A second preview state (`simSteps: [{ over: false }, { over: true }]`) ships the overrun at ratio 1.35.
- **`src/client/render/charts/quota-fit.ts`** — the `quotas` chart's cell geometry as a pure module: `quotaGeometry(barW, boxH, rows, labelH, scale)` picks the tallest square cell that fits vertically and then DERIVES the cell count from the width (`QUOTA_MIN_CELLS` 6, `QUOTA_MAX_CELLS` 32, `QUOTA_GAP_RATIO` 0.18, `QUOTA_BREATHING` 6), so a wide tile gets more cells instead of wider ones.

### Fixed — the Command Code monthly window (2026-09-30)

- **The monthly limit came back on every card.** `/alpha/whoami`, `/alpha/usage/summary` and `/alpha/billing/subscriptions` were measured at **14–21 s on six consecutive calls** while `/alpha/billing/credits` answers in ~1 s — and 3.6–4.2 s twenty minutes later, i.e. that upstream's latency for those three is variable. The host had ONE 8 s budget, so all three were dropped on every poll and the family degraded exactly as the report showed: **Usage Rings** drew two rings instead of three, **Usage Bars** listed the 5-hour and Weekly limits with no Monthly limit row, **Quota Forecast** fell to `-%` with its Budget row at `—` (its projection needs the subscription's plan and period), and the switcher showed `Key 1` / `Key 2` instead of the account names.
- **`src/host/commandcode.ts` now plans per slice.** `credits` keeps 8 s and is the only slice the route waits for; the slow three get 30 s and are refreshed OUT OF BAND. A per-`(member, endpoint)` slice store keeps the last good answer (TTLs: credits `ROUTE_CACHE_MS`, usage 5 min, subscription 10 min, whoami 60 min), a background refresh never blanks a slice we already know, retry floors are 60 s for a stale slice and 15 s for one never seen, and the store is keyed by `ref:tail` so a key rotation cannot serve the previous account's data. A cold route call waits at most `COMMANDCODE_COLD_WAIT_MS` (1500 ms) for slices it has never seen — measured 1 s of credits plus that, against 8 s before — and the host warms every pool member's four slices at boot.
- **The client half** (`src/client/data/collector.tsx`): the extra 5 s look now fires whenever a reply is degraded — including the FIRST, cold answer, which is partial by design — not only when it would have replaced a complete payload. The month therefore appears within ~25 s of a page load instead of waiting for the 60 s poll.

## v1.8.0 — the structure release: two monoliths dissolved, zero type errors, published types

> An engineering release with **no card changes**: the rail, the wave, the settings pages and every widget behave exactly as in v1.7.0. What changed is where the code lives, what the gates can prove, and two long-standing publication defects. Every step was verified against the previous build rather than by eye — the render snapshot (110 outputs), the compiled-CSS concatenation, the host-route fingerprints and the live probes all had to come out identical, and where a change was intended it had to be *provably* that change alone.

### Changed — the two god-files are gone

- **`client/index.ts`: 3,795 → 308 lines.** The right rail's slot body (deck grid, magnification-wave assembly, add panel, sliding drawer) moved to `rail/rail-view.tsx` as `createRailView(deps)`, and its measurement layer (anchor probes, right-bar width tracking, the ResizeObserver fan-out, the budget/YIELD beat and the single complete dispose) to `rail/measure.ts` as `createRailMeasure(deps)`. Both receive the bridge handles they used to close over; the two values the composition root itself owns — `railBudget` (part of the bridge snapshot) and `drawerEl` (written by the rail view's ref) — stay there and cross the boundary through accessors. The move is auditable line by line: the rail body differs from the original in **exactly three lines**, all of them event-handler reads that must observe the live prefs binding rather than a render-time snapshot.

- **The probe learned to tell an upstream miss from a layout defect**: the host route fetches each member's four endpoints independently, so a member can come back with a slice missing under rate limiting (observed while running the suite). The period assertion now records that as the upstream state instead of blaming the card, and the `Key N` label fallback is accepted as naming the view by position.

### Changed — the magnification wave is one spring, written every frame

- **The enter is a continuous spring now, not a CSS tween.** The old shape was a 200ms `settle` transition followed by an untweened `follow`, and no parameter could make it hold a *moving* target: writing a new focus on every pointer frame **retargets** a CSS transition, so it restarts from its current value and never gets past the ease ramp's slow start (measured frame by frame on the real GPU: walking the pointer onto a card gave **0.02–1.1 scale/s** where a single jump gave **3.5** — the enter animated at whatever speed the mouse happened to be moved at). Freezing the target so the tween could finish fixed the curve but left the geometry stale, and the card **snapped** to the live position the moment the freeze ended — the reported "wrong position as soon as I move over the widgets".
- **The progress is an explicit factor** written every animation frame: `displayed[i] = 1 + (target[i] − 1) · p`, where `target` is the live pointer geometry (always current, never a reason to restart anything) and `p` runs `WAVE_SPRING` between rest (`0`) and engaged (`1`). Both are continuous, so their product is: enter, follow and leave become ONE uninterrupted motion on one curve, in both directions, and an interrupted enter reverses from the live `p` instead of jumping. The spring is the Apple-parameterised pair (`response 200ms`, `bounce 0.1`) shared with `dsh-usage-center`'s chart tween — ≈250ms to settle, ~0.15% overshoot (≈0.4px at the default tier). `prefers-reduced-motion` writes `p` in a single frame.
- **The phase machine is gone**: `animPhase` / `settle` / `follow` / `return`, `setPhaseNow` / `setPhaseAfter` / `phaseTimer`, `MORPH_MS` / `SETTLE_MS`. `leaveRail` is now just `armed = false; focus = null` — releasing is the same spring read backwards, so there is no second path to keep in sync and no "tween finished?" boundary to land on the wrong side of.
- **The enter's remaining cost was a compositing one, and the fix is a permanent hint.** The overlay's slots and the add button now carry `will-change: transform` **always**, so their 15 layers exist before the pointer arrives. Measured with the hint gated on the hover (the old shape): the natural enter opened with a **63ms** layer-promotion + raster frame; with it permanent the same enter ran **16ms with zero dropped frames** (`scripts/diag-hover-isolate.cjs`, P4 vs P5). The 64ms "raster prewarm" that used to flip the overlay visible while the rail was idle is REMOVED — it almost never coincided with a real hover, and the stall came back on every enter without the permanent hint.
- **Verified frame by frame** by `docs/verify-rail-morph.cjs` (`HEADFUL=1` for the real GPU, `REDUCED=1` for the reduced-motion path): it samples every frame of a stepped enter, a direct enter and a stepped leave and reports the per-frame speed envelope, so a retargeted curve or a snapped hand-over cannot pass unnoticed — a walked enter peaks at `maxFrameStep` **0.022** against **0.181** for the CSS version at the same geometry, and the reduced-motion enter arrives in one frame. The state machine and the scroll are regression-covered by `scripts/diag-rail-hover-release.cjs` (11 assertions) and `scripts/diag-rail-scroll-perf.cjs`.

### Added — the Settings nav cell wears the app's own glyph

- **The mark is scoped and reversible.** Only that one row is touched —matched by our own label, never by position, so no other plugin's cell is styled —it is re-applied on a language switch (the label is localized), and it is removed with the owning effect, so closing the panel or unloading the plugin leaves no marked node behind. The observer only scans when a `_navList` is inserted, so the transcript's per-frame mutations never pay for it.
- **It had to be restored, not invented**: the CSS half and this mark were written together earlier, but only the CSS landed in a commit —the marking effect was lost with an uncommitted `index.ts` rewrite, which left a rule that matched nothing and put the gear back. (Same failure mode as the loading skeletons below; both halves now live in the tree and in the probes.)
- **Verified live** by `docs/verify-nav-glyph.cjs`: it drives the real settings panel and asserts that exactly ONE row carries the attribute and that the row's label is our registered section label, that the gear svg on that row computes to `display: none`, that its `::before` is a 16×16 inline-SVG mask, that no other nav row is marked, and that zero marked nodes survive the panel closing (screenshot `docs/verify-nav-glyph/nav-glyph.png`).

### Added — continuous corner curvature (continuous corner curvature)

- **Card corners are superellipses, not circular arcs**: `corner-shape: squircle` ramps the curvature in from the straight edges, which is what makes an iOS/Figma-style rounded rectangle read as soft rather than cut. It is native CSS, so the card's border and `box-shadow` follow the same outline (a `clip-path` squircle would slice both off), and an engine without `corner-shape` degrades to a plain round corner with no other change.
- **Two controls, in Settings → Components → Widgets**: the switch (default **ON** — the setting exists so a user can compare) and the **corner gear**, the radius as a share of the card's SHORT side (`12 / 16 / 20 / 24 %`, default 16%). Percent, not px, because the reference keeps the corner-to-side ratio: a 150px card and its magnified 190px copy must not get the same corner. `12%` reproduces the old fixed 16px at side 150.
- **The gear reaches everything that draws a card**: the rail (resting deck and the magnified overlay), the market / Config previews, and the loading skeletons. That wiring is what had been missing — `Prefs` declared both fields, the settings rows wrote them and the previews read them, but the rail's own `CardBody` call passed neither, so the setting only ever changed the previews; `DEFAULTS` was missing the two fields as well (`tsc` reported it).
- **Verified live** by `docs/verify-corner-shape.cjs`: on a 15-card rail it asserts every card carries `dsx-squircle` with the switch ON and the measured radius equal to `shortSide × gear%` (26px at side 160 for the 16% gear), that flipping the switch OFF removes the class from all 15 and flipping it back restores all 15, and that selecting the 24% gear widens every radius to 38px — then restores the values it found.

### Fixed — the Command Code cards no longer freeze on their mount-time numbers

- **Quota Manager's Today / Budget were permanently `—`**: the card reads the day map folded to the `commandcode` route (`stats.commandCodeDaily`), and the client NEVER requested that URL (`/api/widgets-usage-daily?provider=commandcode`) — the contract, the host route and the host's fold were all in place; only the line that asks for it was missing, so `daily` stayed `undefined` and both figures degraded to the dash that means "no such number exists". Wired up; on the real payload the card now renders Today **363M** / Budget **726M** (head 35%).
- **The Command Code monthly ring had vanished, and the quota card's head read `-%`**: one DEGRADED reply (HTTP 200 with a `null` upstream slice) makes `monthlyWindow()` return `null` on purpose — a partial sum would read low — and the client OVERWROTE the last complete payload with it, then only re-asked on mount / turn-settle. `ccPayloadDegraded()` was exported for exactly that "ask once more, shortly" and was never called. One poll in three sampled exactly that way (`keys[].data.*` all `null`, labels fallen back to `Key N`). A degraded reply now never replaces a complete one and schedules one retry 5 s out, and a failed request keeps the previous numbers instead of blanking them (stale-while-error).
- **Idle numbers never moved at all**: these windows are ACCOUNT-wide — another client spending against the same pool moves them with no turn HERE to hang a refetch on — while the old collector pulled only on mount and when a turn settled. That is exactly why the Usage Center moved and the rail did not: usage-center runs its own 2 s poll. The rail now pulls the account payload every 60 s while it is open with a Command Code card installed, pauses while the tab is hidden, and refreshes the moment the tab returns.
- **The cost is measured, not assumed** (2026-09-23): one account tick is four upstream reads per pooled key — 8 reads, 1.06–1.6 s, 4.7 KB on this two-key pool, ≈480 reads/hour — and the `provider=commandcode` day map is a usage-center memo key nothing else asks for, so a cold call re-folds the session logs: **10.6 s and 21.2 s** against 34 ms warm. It therefore runs on the turn-settle and mount paths only, never in a poll loop. All host routes gained a 20 s TTL + single-flight memo, so several tabs, the degraded retry and the two scopes of one settling turn collapse into one upstream pass / one fold (measured cold 1063 ms → 0 ms cached, 6 requests folding 3 times).

## v1.6.1 — the rail scrolls by whole rows, stops at its own content, and releases the hover every time

> A fix release. Three rail defects that survived v1.6.0 are gone: the wheel scrolled in pixels (and could strand a row half up, or refuse to move at all), the deck could be scrolled past its last component into empty space, and the magnification wave could stay engaged after the pointer had left the widgets. Every claim below was measured against the live GUI at 1578×1000 (15 widgets, 2 columns, pitch 184px) and is re-checked by three probe scripts that ship in `scripts/`.

### Fixed — the wheel scrolls in whole rows

- **The last rows could never reach the top.** The rail's scrollable range was the deck's own height minus the viewport, which is shorter than the last row's offset (measured: range 750px with 8 rows × pitch 184), so the browser clamped the final detents and the deck stopped moving while the wheel kept turning. The scrollable content is now derived from the geometry — `contentH = max(rows · pitch, stackHeight) + railViewportHeight` — with the difference reserved by a non-interactive tail inside the rail, so every row can top out and the last one does.
- **Half-scrolled rests.** The wheel's own native scroll lands on the compositor *before* the event reaches the main thread (measured: `scrollTop` was already 120 when the handler ran), so an interrupted animation could leave the deck a third of a row up. The rail now runs its own 240ms tween that always ends on a detent, plus a row guard that snaps any off-grid rest position back onto `2 + row · pitch`.
- **The dependency array that cancelled the tween.** The wheel effect listed `railElRef` — a plain `{ current }` object rebuilt on every parent render — so every parent re-render tore the effect down and its cleanup called `stopTween()` mid-flight. The ref is a real `React.useRef` now and the effect depends only on the card size and gap.
- **Line- and page-mode wheels did nothing or jumped nine rows.** LINE/PAGE deltas are discrete: exactly one event is one detent, whatever its magnitude. Previously a 3-line event (48px) fell below the pixel threshold and a page event (raw `clientHeight`) skipped nine rows.
- **Verified** by `scripts/verify-rail-wheel-matrix.cjs` (single event, a notch split in two, small trackpad ticks, a flick, line mode, page mode, upward flick, long flick to the end) and `scripts/verify-rail-scroll.cjs` (each notch = one pitch, every rest position a whole row, a whole row at the top everywhere, the last row reachable).

### Added — the scroll stops when the components end

- **A threshold instead of an endless tail.** A row may top out only while its own cards still reach into the viewport: `lastRow = ceil((contentBottom + viewportHeight − rowSeat) / pitch) − 1`. Measured: 8 rows, deepest card bottom 1450px, viewport 936px → the deck stops at the 7th detent (1290px) and further notches change nothing (`1290 → 1290`). Before this, four extra detents pulled up nothing but blank space.

### Fixed — the magnification wave always ends when the pointer leaves

- **The safety net was cancelling itself.** A window-level `mousemove` guard had been added to end the wave when the pointer is no longer over a tile — but its effect had no dependency array, so while the wave was live (a re-render per frame) every cleanup cleared the pending release timer. It could never fire. The guard now mounts once and reads its state from refs.
- **"On the widgets" now means ON A TILE, not "inside the rail".** The rail's box is 372 × 936 and mostly empty — its padding, the 24px gaps between cards and every blank run below the last row are all inside it — so the old box test kept the wave alive over gaps, above the first row and right of the last card. Tiles are tested individually with a 7px halo (the gap is 24px, magnified neighbours float ~12px apart), which covers a gap crossing without swallowing the blank areas.
- **Verified on six exit paths** by `scripts/verify-rail-interaction.cjs` — out of the leftmost card, out of the rightmost, down an empty column, down into the band below the deck, above the first row, and a fast diagonal — each one checked with `document.elementFromPoint` so an endpoint that is genuinely over a card is never mistaken for a defect.

## v1.6.0 — the rail obeys the transcript measure, and the panel truly swallows it

> This release ships everything that was tracked as "unreleased" in the previous README — the rail layout rewrite and the measurement/hit-test fixes measured against the live GUI on 2026-09-13 and 2026-09-17 — plus two commits that had been pushed to GitHub but never published (the `context-water` 2×2 slot fix and the website design-audit refactor). It is the first release where the rail derives its own width from the product's transcript measure instead of claiming a fixed 372 px.

### Added — the rail sizes itself from the product's own transcript measure

- **Budget-derived geometry.** The rail may only claim the margin the reading measure leaves over: `budget = official conversation column width − official transcript measure − 74px box inset`. Both numbers are read from the product's own published variables (`--dsh-conversation-column-width`, `--dsh-chat-content-width`), with a live `getBoundingClientRect` read preferred when it exists — the product writes those variables *after* the track transition settles, so a single debounced read can latch a mid-animation value (that is what once drove the budget to 0 and left the rail hidden until the window was resized).
- **A degradation ladder instead of a fixed claim.** Preferred layout → one column fewer → a narrowed single column (side ≥ 100px) → yield the field entirely (`--dsx-rail-w: 0`, nothing rendered, the user's preferences untouched, and the rail returns by itself when the window grows again).
- **The rail can no longer squeeze the reading column.** The inset rule lost its `!important`; because the claim is computed from the measure it can never exceed the leftover margin, so the only possible failure mode is collapsing — never compressing the transcript below the product's `clamp(680px, …, 920px)` floor.
- **The header capsule reports the same state.** With no room it renders `data-space="tight"` (dimmed, `aria-disabled`, `cursor: not-allowed`) instead of openable-but-empty.
- **Measured** (viewport → rail / transcript): 1578 → 372 / 748 px, 1400 → 198 / 748 px, 1280 → 154 / 748 px, 1120 → yielded / 664 px. Every one of those transcript widths is the product's own measure for that column; before this change the rail hard-claimed 372 px and drove the transcript to 554 px (1280) and 394 px (1120).

### Changed — the right panel now swallows the rail instead of the rail fading beside it

- **Layer order was the real problem, not opacity.** Probed with `elementFromPoint` over a fixed test block injected into each candidate host: inside `shell.overlay` the block paints *above* the official panel (z-20 vs the panel's z-10), inside the conversation subtree it paints *below* it. The rail's host moved from `shell.overlay` to `conversation.input.overlay` — the official list slot for "floating entries rendered inside the resident composer card" — so the panel sweeps across the rail and hides it segment by segment, exactly like a drawer being covered.
- **Pinning instead of animating.** While a panel exists (opening, open, or closing) the rail pins to the viewport's right edge via one variable, `--dsx-rail-right`; with no panel that resolves to the same value as the conversation-column anchor, so the switch is invisible. Closing retreats the panel and re-exposes the rail progressively. The variable also drives the magnify overlay and the settings drawer, so no rail-owned surface can stay parked over the panel.
- **Panel presence is read as `max(inline target, measured width)`.** On the first frame of the close animation the frame's inline grid target already reads `0px`; trusting it would snap the rail back under a panel that is still covering it.
- **One curve for track and occupant.** The transcript inset now uses the official `--ds-transition-duration-slow` / `--ds-ease-in-out` tokens instead of `0.2s ease`, matching the track's own animation — the layout package lists "track and occupant share one curve" as an invariant, and 0.2s/ease was visibly out of step with the 0.3s track. The composer-overlay seat (which is positioned against the scroll body's padding box, so it follows the rail's width) is on the same rule.
- **Invisible surfaces stop eating pointer events.** `[data-yielded]` (faded out because the panel owns the space) and `.dsx-stats-drawer[data-no-room]` (faded out with nothing covering it) now set `pointer-events: none`, so a see-through rail can no longer swallow hovers and clicks meant for the transcript or for the product's column-width drag band.

### Changed — native rail follow via CSS anchor positioning

- **The rail rides the product's own layout pass.** `[data-phase='active']` (the conversation host — measured to share the center column's box exactly; the hashed `_centerCol` class remains as a fallback, selected only when that seam is absent, so exactly one element ever owns the name) carries `anchor-name: --dsx-center`, and the rail's `right` is `anchor(--dsx-center right, var(--dsx-rightbar-w, var(--dsh-sidebar-width, 0px)))`. Anchor resolution happens in the same style→layout pass that animates the shell's `grid-template-columns` track. Measured per frame: `|center column right − rail right| = 0.00px` over a full open/close.
- **The JS follow path stopped writing a `:root` variable every frame** (a per-frame root-variable write invalidates style for the whole document); it is now only the fallback for browsers without anchor positioning, and it writes the settled value once, 200ms after the motion ends.
- **The ResizeObserver is re-bound lazily on every measure** (`observeMeasured()`), which is idempotent and self-heals when the shell re-creates its nodes. The old observer was constructed during `apply()` — before the Web UI mounts its frame — so every `querySelector` returned `null` and it observed **zero** elements (verified in-browser: 19 live `ResizeObserver`s on the page, none on `[class$='_rightbarCol']`). That is why the rail used to sit still through the sidebar's 300ms track animation and then jump into place.
- **Start and end with the panel.** The AppFrame's `transitionrun` for `grid-template-columns` plus the frame's inline grid target let the rail predict the final column width on the animation's first frame (the observer's first delivery trails it by ~100ms), so the rail's retreat and the panel's push run on the same beat instead of the rail arriving late.
- **Boot no longer plays the enter animation** when the preference says "open" but the session is not known yet: that first-paint slide had no valid containing block for the anchor (a transformed ancestor), so `anchor()` resolved to nothing and the rail painted at the left edge for ~2.6s before jumping. Restored layouts now appear in place; a user-initiated open still glides.

### Fixed — hovering the rail re-rendered the entire rail on every pointer frame

- **Measured before** (headed Edge, 1600×900): p50 frame 12.5ms, p95 41.8ms, max 129ms, 15 frames > 26ms, 598ms of JS across 2.6s of hovering — against a 4.2ms idle baseline. **After**: p50 4.2ms, p95 8.3ms, 1 frame > 26ms, 193ms of JS, i.e. back at the idle baseline.
- **Root cause**: the magnification wave owned its focus state in the same component that also built the resting deck, the widget list and the always-mounted add panel, so every pointer frame re-rendered every widget's `render()` output and the settings page inside the add panel.
- **Fix**: the wave is now its own `RailWave` component; the deck and the add panel are built by the parent, whose element identity stays stable while the pointer moves, so React bails out of those subtrees entirely (only the overlay's 7–15 slot divs reconcile per frame).
- **Fix**: magnified copies are sized with `transform: scale()` about a `top-right` origin instead of `width`/`height` — the same geometry, verified slot by slot (visual width == `baseW × scale`, right-edge delta 0), with the per-frame cost moved to the compositor.
- **Fix**: the resting deck fades through a `.dsx-wave-deck.dsx-wave-on` class (cards and the add button) instead of an inline per-slot opacity, so engaging the wave no longer re-renders the deck at all.

### Fixed — three symptoms reported against the live GUI (2026-09-17)

**Fix — rail open/close glide returns to main-thread `right` transition for perfect lockstep (with dsh-ui-harmonizer v0.8.3):**

## v1.2.1
**Fixed — the last edit is now flushed to the host store when the page closes, so widget state survives ANY desktop shell and every browser/device:**

- **Root cause.** Widget config is written to two channels: `localStorage` (fast path) and the host file via a **400 ms debounced** PUT to `/api/widgets-state` (authoritative, origin-independent). The debounced write had **no unload flush**: if the window/tab closed within that 400 ms window (or while the PUT was still in flight), the request died with the page. On shells that spawn a fresh random loopback origin per launch (e.g. DSH Desktop builds), `localStorage` is a brand-new realm on every boot, so that single missed PUT meant the edit was lost for good — "changes don't save" on desktop while the fixed-port local web (stable origin) masked the same defect invisibly.
- 💾 **Unload flush.** A `pagehide` listener now calls `flushPendingState()` the moment the page starts tearing down. It sends any state that has not yet reached the host store via `navigator.sendBeacon` (delivered by the browser even as the page is destroyed) with a keepalive-fetch fallback; the host route already accepted POST as well as PUT, so the same endpoint copes with it. A quick close after an edit can no longer lose the change, on any desktop shell, browser origin, private mode, or cleared-site-data session.
- 🛡️ The debounced PUT also gained `keepalive: true`, so a write already in flight survives page teardown as well.
- 🧪 Headless-verified end-to-end against the real host store: capsule-click (a real `setPrefs` → `saveState`) followed by an **immediate** `pagehide` (≈80 ms, well inside the 400 ms debounce) produced a real beacon; the host file's `savedAt` advanced to match `localStorage`, the debounce fetch did not re-fire, and the test restored the user's true state afterwards.

## v1.1.5
**Fixed — widget state now survives restarts (root cause: browser `localStorage` only):**

- 🔄 On boot the client syncs with the host store: whichever side (localStorage vs host file) holds the newer `savedAt` wins, so any origin/browser converges to the last saved configuration instead of resetting; every change is written to both channels (localStorage immediately, host via a 400 ms debounced PUT).
- 🖥️ Cross-tab + visibility re-sync: a `storage` event re-reads the configuration in sibling tabs of the same origin, and switching back to a tab re-pulls the host store — multi-window/multi-origin sessions converge live, not only on the next boot.
